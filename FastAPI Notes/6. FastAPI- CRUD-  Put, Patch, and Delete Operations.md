## 1. CRUD Overview — What We're Completing

| Operation | HTTP Method | Status Code | Endpoint Example |
|---|---|---|---|
| **C**reate | `POST` | 201 Created | `POST /api/posts` |
| **R**ead | `GET` | 200 OK | `GET /api/posts/{id}` |
| **U**pdate (full) | `PUT` | 200 OK | `PUT /api/posts/{id}` |
| **U**pdate (partial) | `PATCH` | 200 OK | `PATCH /api/posts/{id}` |
| **D**elete | `DELETE` | 204 No Content | `DELETE /api/posts/{id}` |

> **Interview Tip:** Always know which HTTP method maps to which CRUD operation and which status code is returned. This is a very common interview question.

## 2. PUT vs PATCH — Key Difference

| | PUT | PATCH |
|---|---|---|
| Type | Full replacement | Partial update |
| Fields required | All fields required | Only changed fields |
| Missing fields | Overwrite with defaults | Keep existing values |
| Common use | Replace entire resource | Update one or two fields |
| More practical? | Less common | ✅ More commonly used |

> **Important:** With PUT, if you only send a title but forget content, content gets overwritten with `null` or default. With PATCH, missing fields are left untouched. PATCH is almost always the better choice for user-facing APIs.

## 3. PostUpdate Schema — Optional Fields for PATCH

```python
# schemas.py
class PostUpdate(BaseModel):
    title: str | None = Field(default=None, min_length=1, max_length=100)
    content: str | None = Field(default=None, min_length=1)
```

- All fields are `str | None` with `default=None` — making them optional.
- Field validations **still apply** if a value is provided — e.g. title still must be ≥ 1 character.
- `user_id` is intentionally excluded — you don't want clients changing post ownership via a PATCH.

> **Interview Tip:** To allow changing ownership you would use a dedicated endpoint or PUT — not a partial PATCH. This is an important API design decision.

## 4. PUT Endpoint — Full Update

```python
@app.put("/api/posts/{post_id}", response_model=PostResponse)
def update_post_full(post_id: int, post_data: PostCreate, db: db_dependency):
    result = db.execute(select(models.Post).where(models.Post.id == post_id))
    post = result.scalars().first()

    if not post:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Post not found")

    # Validate new user_id if ownership is changing
    if post_data.user_id != post.user_id:
        user_result = db.execute(select(models.User).where(models.User.id == post_data.user_id))
        if not user_result.scalars().first():
            raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="User not found")

    # Update all fields
    post.title = post_data.title
    post.content = post_data.content
    post.user_id = post_data.user_id

    db.commit()
    db.refresh(post)
    return post
```

- Uses `PostCreate` schema — all fields are **required**.
- Checks if post exists → 404 if not.
- Validates the new `user_id` if ownership is changing — gives a friendly error instead of a raw DB constraint error.
- Directly assigns all fields (explicit, predictable).

## 5. PATCH Endpoint — Partial Update

```python
@app.patch("/api/posts/{post_id}", response_model=PostResponse)
def update_post_partial(post_id: int, post_data: PostUpdate, db: db_dependency):
    result = db.execute(select(models.Post).where(models.Post.id == post_id))
    post = result.scalars().first()

    if not post:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Post not found")

    # Only update fields the client actually sent
    update_data = post_data.model_dump(exclude_unset=True)
    for field, value in update_data.items():
        setattr(post, field, value)

    db.commit()
    db.refresh(post)
    return post
```

- Uses `PostUpdate` schema — all fields are **optional**.
- `model_dump(exclude_unset=True)` — only includes fields the client actually sent.
- `setattr(post, field, value)` — dynamically sets each field on the model object.

---

## 6. `exclude_unset` — The Key to Correct PATCH

```python
post_data.model_dump(exclude_unset=True)
```

### Without `exclude_unset=True`

```
Client sends: {"title": "New Title"}
model_dump() returns: {"title": "New Title", "content": None}
Result: content gets set to None ❌ — existing content is wiped out
```

### With `exclude_unset=True`

```
Client sends: {"title": "New Title"}
model_dump(exclude_unset=True) returns: {"title": "New Title"}
Result: only title is updated, content unchanged ✅
```

> **Important:** `exclude_unset=True` is what makes PATCH work correctly. Without it, a PATCH behaves like a PUT and wipes out any field not sent by the client.

### `setattr()` for dynamic field updates

```python
for field, value in update_data.items():
    setattr(post, field, value)
# Equivalent to: post.title = "New Title"
```

- `setattr(obj, "title", "New Title")` is the same as `obj.title = "New Title"`.
- Useful when you don't know which fields will be updated at write time — handles it dynamically.

## 7. DELETE Endpoint — 204 No Content

```python
@app.delete("/api/posts/{post_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_post(post_id: int, db: db_dependency):
    result = db.execute(select(models.Post).where(models.Post.id == post_id))
    post = result.scalars().first()

    if not post:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Post not found")

    db.delete(post)
    db.commit()
    # No return needed — 204 means no response body
```

- `@app.delete()` — maps to the DELETE HTTP method.
- No `response_model` — 204 responses have no body.
- `status_code=HTTP_204_NO_CONTENT` — tells the client the operation succeeded with nothing to return.
- `db.delete(post)` → `db.commit()` — stages and executes the deletion.

> **Interview Tip:** Always return 204 (not 200) for successful deletions. 200 implies a response body; 204 explicitly signals "success, nothing to return."

## 8. User Update Schema

```python
class UserUpdate(BaseModel):
    username: str | None = Field(default=None, min_length=1, max_length=50)
    email: EmailStr | None = Field(default=None, max_length=120)
    image_file: str | None = Field(default=None, min_length=1, max_length=200)
```

- Same pattern as `PostUpdate` — all optional, validations still apply if provided.
- Includes `image_file` — lets users update their profile picture filename.
- Does **not** include password — password changes need a separate dedicated endpoint for security.

### Manual field update approach (alternative to `setattr` loop)

```python
if user_data.username is not None:
    user.username = user_data.username
if user_data.email is not None:
    user.email = user_data.email
if user_data.image_file is not None:
    user.image_file = user_data.image_file
```

- Both approaches (manual `if` checks and `setattr` loop) are valid.
- Manual is more readable for small models; `setattr` loop scales better for large models.

## 9. Cascade Delete — Users and Their Posts

### The problem

When a user is deleted, what happens to their posts?
- Option A: Block deletion if the user has posts.
- Option B: **Cascade delete** — delete the user and all their posts automatically. ✅

### Setting up cascade delete in models.py

```python
class User(Base):
    __tablename__ = "users"
    # ...
    posts: Mapped[list[Post]] = relationship(
        "Post",
        back_populates="author",
        cascade="all, delete-orphan"   # ← adds cascade delete
    )
```

- `cascade="all, delete-orphan"` — tells SQLAlchemy to delete all related posts when the user is deleted.
- `delete-orphan` — also cleans up posts that are somehow removed from the relationship without being explicitly deleted.

### Delete user endpoint

```python
@app.delete("/api/users/{user_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_user(user_id: int, db: db_dependency):
    result = db.execute(select(models.User).where(models.User.id == user_id))
    user = result.scalars().first()

    if not user:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="User not found")

    db.delete(user)
    db.commit()
    # Cascade automatically deletes all user's posts
```

> **Important:** Use cascade delete with caution in production. Always warn users before deleting an account — "This will permanently delete all your data." Some platforms require typing the account name to confirm.

> **Interview Tip:** Cascade delete is set on the **relationship** in the model, not on the delete endpoint. The endpoint just deletes the user; SQLAlchemy handles the rest automatically.

## 10. HTTP Status Code Reference

| Code | Name | When to Use |
|---|---|---|
| `200` | OK | Successful GET, PUT, or PATCH |
| `201` | Created | Successful POST (resource created) |
| `204` | No Content | Successful DELETE (no body returned) |
| `400` | Bad Request | Duplicate username or email |
| `404` | Not Found | Resource doesn't exist |
| `422` | Unprocessable Content | Validation error (automatic from Pydantic) |

> **Common Question:** *"What status code should a DELETE endpoint return?"*
> `204 No Content` — the operation succeeded but there is nothing to return in the response body.

> **Common Question:** *"What is the difference between 400 and 422?"*
> 400 is for business logic errors (e.g. duplicate username). 422 is for data format/validation errors (e.g. invalid email format) — FastAPI returns 422 automatically via Pydantic.

## 11. Profile Picture Update Pattern

- Only the **filename** is stored in the database (e.g. `corey.png`).
- The full path is computed by the `@property` on the User model:

```python
@property
def image_path(self) -> str:
    if self.image_file:
        return f"/media/profile_pictures/{self.image_file}"   # user uploaded
    return "/static/profile_pictures/default.jpeg"            # default
```

- Updating the profile picture = PATCH the `image_file` field with the filename.
- File upload functionality (actually sending the file) is added separately in a later step.

> **Interview Tip:** Storing only the filename decouples the database from the file system. If you reorganize folders later, you only update the path-building logic — not every database row.

## 12. Common Interview Questions

**Q: What is the difference between PUT and PATCH?**
> PUT is a full replacement — all fields are required and the entire resource is overwritten. PATCH is a partial update — only the fields you send are changed; everything else stays the same. PATCH is more practical for most real-world APIs.

---

**Q: How do you implement partial updates correctly in FastAPI with Pydantic?**
> Make all fields optional in the schema (`field: str | None = None`). Use `model_dump(exclude_unset=True)` to get only the fields the client sent. Loop over the result with `setattr()` to dynamically update only those fields.

---

**Q: What does `exclude_unset=True` do in Pydantic's `model_dump()`?**
> It returns only the fields that were explicitly set by the client, excluding fields that were left as defaults. Without it, PATCH would behave like PUT and overwrite missing fields with `None`.

---

**Q: What HTTP status code should a DELETE endpoint return?**
> 204 No Content. It signals the request succeeded but there is no response body. Do not use 200 for deletions — 200 implies a response body.

---

**Q: What is cascade delete in SQLAlchemy?**
> It's configured on a relationship with `cascade="all, delete-orphan"`. When the parent record (e.g. User) is deleted, SQLAlchemy automatically deletes all related child records (e.g. Posts). Without cascade, deleting a user with posts would cause a foreign key constraint error.

---

**Q: How do you check for duplicate values before creating or updating a user?**
> Query the database for the value before inserting. If a result is found, raise an `HTTPException` with `status_code=400` and a descriptive detail message. This gives a user-friendly error instead of a raw database constraint violation.

---

**Q: Why not include `user_id` in the `PostUpdate` (PATCH) schema?**
> Changing ownership via a partial update is generally not desired behavior. If you need to reassign a post, use a PUT (full replacement) or a dedicated ownership-transfer endpoint. Leaving `user_id` out of PATCH prevents accidental or malicious ownership changes.

## 13. Common Mistakes & Pitfalls

> **Pitfall:** Not using `exclude_unset=True` in PATCH — fields not sent by the client get overwritten with `None`, effectively making PATCH behave like PUT.

> **Pitfall:** Returning 200 instead of 204 for DELETE — 200 implies a response body; 204 is the correct signal for "success, nothing to return."

> **Pitfall:** Forgetting to validate the new `user_id` in a PUT update — if the new user doesn't exist, the database throws a foreign key constraint error instead of a clear 404.

> **Pitfall:** Not setting `cascade="all, delete-orphan"` before implementing user delete — deleting a user with posts will cause a foreign key constraint error.

> **Pitfall:** Including `response_model` on a 204 DELETE endpoint — there is no body to serialize; remove it.

> **Pitfall:** Updating ownership via PATCH — always exclude ownership fields (like `user_id`) from partial update schemas.

> **Pitfall:** Not checking for duplicate usernames/emails before updating — the DB constraint will fail with an unhelpful error.

---

## 14. Best Practices

- Use PATCH over PUT for most update endpoints — it's more user-friendly and flexible.
- Always make all fields optional in update schemas and use `exclude_unset=True`.
- Use `setattr()` loop for dynamic updates on large models; manual `if` checks for small models.
- Always validate that related records (e.g. new `user_id`) exist before updating foreign keys.
- Return 204 (not 200) for successful deletions.
- Configure `cascade="all, delete-orphan"` on relationships where child records should be cleaned up automatically.
- Warn users in production before cascade deletion — irreversible operations need explicit confirmation.
- Keep password changes in a dedicated endpoint — never in the general user update endpoint.
- Avoid exposing ownership-change logic through PATCH — use PUT or a dedicated endpoint.
- Use `status.HTTP_XXX_NAME` constants throughout for readability and self-documentation.
