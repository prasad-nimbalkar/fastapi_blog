## 1. PUT vs PATCH — Full vs Partial Updates

### Core Concept Definition

Two HTTP methods exist for updating resources — and interviewers test this distinction often:

| Method | Description | When to Use |
|---|---|---|
| **PUT** | **Full replacement** — client sends ALL fields; missing fields are reset | Replacing an entire resource |
| **PATCH** | **Partial update** — client sends only changed fields; rest stays untouched | Updating one or two fields |

> **Why it matters:** Using PUT when you should use PATCH forces API clients to always send the entire object — a poor developer experience and a source of accidental data loss.

### Interview-Relevant Details

- **PUT is idempotent:** Sending the same PUT request multiple times produces the same result
- **PATCH may or may not be idempotent** depending on implementation
- In practice, **PATCH is used more often** in real-world REST APIs
- Both PUT and PATCH typically return `200 OK` with the updated resource, or `204 No Content` if you don't return the resource

### Common Interview Questions & Answers

❓ **"What is the difference between PUT and PATCH?"**
> PUT replaces the entire resource — all fields are required. PATCH updates only the provided fields — everything else stays the same. PATCH is more practical for most real-world update scenarios.

❓ **"Is PUT idempotent? Is PATCH?"**
> PUT is always idempotent by definition — sending the same full replacement twice yields the same state. PATCH *can* be idempotent (setting a field to a specific value), but isn't guaranteed to be (e.g., an "increment by 1" patch).

❓ **"When would you use PUT over PATCH?"**
> When clients need to fully replace a resource, or when you want to force them to explicitly send every field (e.g., configuration objects where omission means "clear this setting").

### Practical Code Example

```python
from fastapi import APIRouter, Depends, HTTPException, status

router = APIRouter()

# PUT — Full update (all fields required via PostCreate schema)
@router.put("/posts/{post_id}", response_model=PostResponse)
async def update_post_full(
    post_id: int,
    post_data: PostCreate,          # All fields required
    db: AsyncSession = Depends(get_db)
):
    result = await db.execute(select(Post).where(Post.id == post_id))
    post = result.scalar_one_or_none()
    if not post:
        raise HTTPException(status_code=404, detail="Post not found")

    post.title = post_data.title       # Must update ALL fields
    post.content = post_data.content
    post.user_id = post_data.user_id
    await db.commit()
    await db.refresh(post)
    return post

# PATCH — Partial update (all fields optional via PostUpdate schema)
@router.patch("/posts/{post_id}", response_model=PostResponse)
async def update_post_partial(
    post_id: int,
    post_data: PostUpdate,           # All fields optional
    db: AsyncSession = Depends(get_db)
):
    result = await db.execute(select(Post).where(Post.id == post_id))
    post = result.scalar_one_or_none()
    if not post:
        raise HTTPException(status_code=404, detail="Post not found")

    # Only update fields that were actually sent
    update_data = post_data.model_dump(exclude_unset=True)
    for field, value in update_data.items():
        setattr(post, field, value)

    await db.commit()
    await db.refresh(post)
    return post
```

### 🎯 Interview Tip
A strong answer mentions **idempotency**, **developer experience**, and **accidental data loss risk with PUT**. Bonus points for mentioning that most real-world APIs prefer PATCH for day-to-day updates and PUT only for full resource replacement.

## 2. Pydantic Schemas for Updates — Optional Fields Pattern

### Core Concept Definition

For PATCH endpoints, you need a separate schema where **all fields are optional** — because the client only sends what they want to change.

The standard pattern:
1. `BaseSchema` — shared field definitions with validators
2. `CreateSchema(BaseSchema)` — all fields required (inherits from base)
3. `UpdateSchema` — same fields but all `Optional[type] = None`
4. `ResponseSchema(BaseSchema)` — adds DB-generated fields like `id`, `created_at`

### Interview-Relevant Details

- `Optional[str]` in Python typing means `str | None` (the field accepts a string or None)
- **Pydantic validators still run** on optional fields when a value IS provided — you get validation without forcing the field to be present
- Don't reuse `CreateSchema` for PATCH — it forces all fields to be present, defeating the purpose
- **Don't expose fields that shouldn't be updatable** (e.g., `user_id` in a post update, `created_at`, `id`)

### Practical Code Example

```python
from pydantic import BaseModel, Field
from typing import Optional

# Base — shared field definitions + validators
class PostBase(BaseModel):
    title: str = Field(..., min_length=1, max_length=100)
    content: str = Field(..., min_length=1)

# Create — all fields required (inherits validators from base)
class PostCreate(PostBase):
    user_id: int

# Update — all fields optional, validators still apply if provided
class PostUpdate(BaseModel):
    title: Optional[str] = Field(None, min_length=1, max_length=100)
    content: Optional[str] = Field(None, min_length=1)
    # Note: user_id intentionally excluded
    # Changing ownership should be a separate, explicit operation

# Response — adds DB-generated fields
class PostResponse(PostBase):
    id: int
    user_id: int
    author: UserResponse

    class Config:
        from_attributes = True  # Pydantic v2 (was orm_mode in v1)
```

### Common Interview Questions & Answers

❓ **"Why do you have separate Create and Update schemas?"**
> Create schemas require all fields. Update schemas make all fields optional so clients don't have to re-send unchanged data. Reusing the Create schema for PATCH would force clients to send every field, turning PATCH into PUT.

❓ **"Why is `user_id` excluded from the Update schema?"**
> Changing resource ownership through a partial update endpoint is a security and design smell. If you need to reassign ownership, that should be an explicit, auditable operation — either a dedicated endpoint or a PUT with full resource replacement.

❓ **"Do Pydantic validators still apply to Optional fields?"**
> Yes. If the field is `None` (not provided), the validator is skipped. But if the client sends a value, all validators run normally. You get optional-but-validated fields.

### 🎯 Interview Tip
Mentioning that `user_id` is deliberately excluded from update schemas — and explaining *why* — signals strong API design instincts. Interviewers at BFSI/fintech companies especially appreciate security-conscious design thinking.

## 3. `exclude_unset` — The Key to Correct PATCH Behavior

### Core Concept Definition

`model_dump(exclude_unset=True)` returns only the fields the client **actually sent** in the request body — not fields that defaulted to `None`.

> **Why this matters:** Without it, optional fields with `default=None` would be included in the update, silently overwriting existing data with `None`.

### The Problem It Solves

```python
# Client sends: { "title": "New Title" }
# PostUpdate schema: title=Optional, content=Optional (default None)

# ❌ WITHOUT exclude_unset=True
post_data.model_dump()
# → {"title": "New Title", "content": None}
# This would wipe out the existing content!

# ✅ WITH exclude_unset=True
post_data.model_dump(exclude_unset=True)
# → {"title": "New Title"}
# Only the sent field is returned — content is untouched
```

### Interview-Relevant Details

- `exclude_unset=True` — excludes fields not set by the client (even if they have defaults)
- `exclude_none=True` — excludes fields whose value is `None` (different! explicitly setting `null` would also be excluded)
- `exclude_defaults=True` — excludes fields equal to their default value
- For PATCH, **`exclude_unset` is almost always what you want**

### Practical Code Example

```python
@router.patch("/posts/{post_id}")
async def update_post_partial(post_id: int, post_data: PostUpdate, db: AsyncSession = Depends(get_db)):
    # ... fetch post, raise 404 if not found ...

    # Get only the fields the client actually sent
    update_data = post_data.model_dump(exclude_unset=True)
    # e.g., if client sent {"title": "New"}, update_data = {"title": "New"}

    for field, value in update_data.items():
        setattr(post, field, value)

    await db.commit()
    await db.refresh(post)
    return post
```

### Common Interview Questions & Answers

❓ **"What does `exclude_unset=True` do in Pydantic?"**
> It returns only the fields that were explicitly set in the incoming request body, excluding fields that received their default values. This is essential for PATCH endpoints to avoid accidentally overwriting existing data with `None`.

❓ **"What's the difference between `exclude_unset` and `exclude_none`?"**
> `exclude_unset` excludes fields the client didn't send at all. `exclude_none` excludes fields whose value is `None`, even if the client explicitly sent `null`. For PATCH, `exclude_unset` is correct — `exclude_none` would prevent clients from intentionally clearing a field.

### 🎯 Interview Tip
This is a **common gotcha question** in mid-level FastAPI interviews. Candidates who only know `exclude_none` and not `exclude_unset` reveal limited real-world PATCH experience. Knowing the distinction is a strong signal.

## 4. `setattr` for Dynamic Field Updates

### Core Concept Definition

`setattr(obj, field_name, value)` dynamically sets an attribute on an object using a string name. Used in PATCH endpoints to apply only the fields returned by `exclude_unset`.

> **Why it's used:** Instead of writing `if post_data.title: post.title = post_data.title` for every field, you loop over the dictionary and set fields dynamically — cleaner and scales with any number of fields.

### Two Approaches: Dynamic vs Manual

```python
# ✅ Dynamic — scales with any schema size
update_data = post_data.model_dump(exclude_unset=True)
for field, value in update_data.items():
    setattr(post, field, value)

# ✅ Manual — explicit, easy to read for small schemas
if post_data.username is not None:
    db_user.username = post_data.username
if post_data.email is not None:
    db_user.email = post_data.email
```

Both are valid. **Dynamic is better for larger schemas**; manual is fine for 2–3 fields and is more readable to less experienced teammates.

### Common Interview Questions & Answers

❓ **"What is `setattr` and why use it in a PATCH handler?"**
> `setattr(obj, name, value)` sets an object attribute dynamically at runtime using a string name. In PATCH handlers, after calling `model_dump(exclude_unset=True)`, you get a dictionary of only the changed fields. Looping with `setattr` applies those changes without writing an `if` block per field.

### 🎯 Interview Tip
Showing both approaches and explaining the trade-off (dynamic = scalable, manual = readable) demonstrates engineering maturity. Neither is wrong — the right choice depends on schema size and team context.

## 5. DELETE Endpoint & HTTP 204 No Content

### Core Concept Definition

A DELETE endpoint removes a resource. The standard response for a successful delete is **`204 No Content`** — the request succeeded, but there's nothing to return.

### Interview-Relevant Details

- `status_code=204` → no response body → **no `response_model`**
- Always check the resource exists first — return `404` if not found
- In production, add **authorization checks** — only the resource owner should be able to delete
- Consider **soft delete** (marking as deleted) vs **hard delete** (actually removing) for audit-trail requirements — common in BFSI

### Practical Code Example

```python
@router.delete("/posts/{post_id}", status_code=status.HTTP_204_NO_CONTENT)
# Note: no response_model — 204 returns no body
async def delete_post(post_id: int, db: AsyncSession = Depends(get_db)):
    result = await db.execute(select(Post).where(Post.id == post_id))
    post = result.scalar_one_or_none()

    if not post:
        raise HTTPException(status_code=404, detail="Post not found")

    await db.delete(post)   # await required — async session interaction
    await db.commit()
    # No return needed — 204 means "success, no content"
```

### Common Interview Questions & Answers

❓ **"What status code should a DELETE endpoint return?"**
> `204 No Content` for a successful deletion with no response body, or `200 OK` if you return a confirmation message or the deleted object. `204` is the REST convention for deletions.

❓ **"What is soft delete vs hard delete?"**
> Hard delete physically removes the record from the database. Soft delete adds a `deleted_at` timestamp or an `is_deleted` boolean — the record stays in the DB but is filtered out of queries. Soft delete is preferred in financial/compliance systems for audit trails.

### 🎯 Interview Tip
Mentioning **soft delete** unprompted in BFSI/fintech interviews is a strong signal. Financial systems almost never hard-delete records — they need audit trails. Saying "in a production financial system, I'd implement soft delete for compliance" is impressive.

## 6. Cascade Delete with SQLAlchemy

### Core Concept Definition

**Cascade delete** automatically deletes related child records when a parent record is deleted. When a `User` is deleted, all their `Post` records are deleted too — without needing explicit code to delete each post.

### Interview-Relevant Details

- Configured on the **relationship**, not the column
- `cascade="all, delete-orphan"` is the standard setting
- `delete` — deletes children when parent is deleted
- `delete-orphan` — also deletes children if they're removed from the relationship without explicit deletion (e.g., `user.posts.remove(post)`)
- **Alternative:** Configure cascade at the **database level** with `ON DELETE CASCADE` on the foreign key — more performant for bulk deletes

### Practical Code Example

```python
# models.py

class User(Base):
    __tablename__ = "users"

    id = Column(Integer, primary_key=True)
    username = Column(String, unique=True)

    # cascade="all, delete-orphan" — deletes posts when user is deleted
    posts = relationship(
        "Post",
        back_populates="author",
        cascade="all, delete-orphan"
    )

class Post(Base):
    __tablename__ = "posts"

    id = Column(Integer, primary_key=True)
    user_id = Column(Integer, ForeignKey("users.id"))  # FK still needed

    author = relationship("User", back_populates="posts")
```

```python
# What happens when you delete a user:
await db.delete(user)   # SQLAlchemy automatically deletes all user.posts
await db.commit()       # Both user and their posts are removed
```

### Database-Level Cascade (Alternative)

```python
# More performant for large datasets — handled by DB engine, not SQLAlchemy
user_id = Column(Integer, ForeignKey("users.id", ondelete="CASCADE"))

# With this, SQLAlchemy relationship needs passive_deletes=True
posts = relationship("Post", back_populates="author", passive_deletes=True)
```

### Common Interview Questions & Answers

❓ **"What is cascade delete and when would you use it?"**
> Cascade delete automatically removes related child records when a parent is deleted. Use it when child records have no meaning without the parent — e.g., posts belonging to a deleted user. Avoid it when child records have independent value or need to be preserved for auditing.

❓ **"What is the difference between `cascade="delete"` and `cascade="delete-orphan"`?"**
> `delete` only triggers deletion when the parent is explicitly deleted. `delete-orphan` *also* triggers deletion when a child is removed from the parent's collection (e.g., `user.posts.remove(post)`). Together as `"all, delete-orphan"` they cover all removal scenarios.

❓ **"What is the alternative to ORM-level cascade?"**
> Database-level `ON DELETE CASCADE` on the foreign key constraint. This is more performant (the DB handles it in a single operation) but less visible in application code. In SQLAlchemy, you'd pair it with `passive_deletes=True` on the relationship.

### 🎯 Interview Tip
Interviewers at data engineering roles often follow up with: *"What are the risks of cascade delete in production?"* Good answer: data loss is irreversible, so always warn users first (like a confirmation dialog), consider soft delete for compliance data, and test cascade behavior in staging before production.

## 7. HTTP Status Codes Reference for REST APIs

### Core Concept Definition

HTTP status codes are standardized numeric responses that tell the client what happened with their request. Using them correctly is a **basic but important** REST API design requirement.

### Complete Reference Table

| Code | Name | When to Use |
|---|---|---|
| **200** | OK | Successful GET, PUT, PATCH |
| **201** | Created | Successful POST (resource created) |
| **204** | No Content | Successful DELETE (nothing to return) |
| **400** | Bad Request | Client error — validation failure, duplicate username/email |
| **401** | Unauthorized | Not authenticated (no/invalid token) |
| **403** | Forbidden | Authenticated but not allowed (wrong user) |
| **404** | Not Found | Resource doesn't exist |
| **409** | Conflict | Resource already exists (alternative to 400 for duplicates) |
| **422** | Unprocessable Entity | Pydantic validation error (FastAPI default) |
| **500** | Internal Server Error | Unhandled server-side exception |

### FastAPI Default Behavior

```python
# FastAPI automatically returns 422 for Pydantic validation errors
# e.g., sending a string where an int is expected

# You control others explicitly:
raise HTTPException(status_code=404, detail="Post not found")
raise HTTPException(status_code=400, detail="Username already taken")

# Or set on the decorator:
@router.delete("/posts/{id}", status_code=status.HTTP_204_NO_CONTENT)
@router.post("/users", status_code=status.HTTP_201_CREATED)
```

### Common Interview Questions & Answers

❓ **"What's the difference between 401 and 403?"**
> `401 Unauthorized` means the client isn't authenticated — they need to provide credentials. `403 Forbidden` means they're authenticated but lack permission — they're logged in but can't do that action.

❓ **"When would you use 409 vs 400 for a duplicate username?"**
> Both are acceptable. `400 Bad Request` is a general client error. `409 Conflict` is more semantically accurate — the request is structurally valid, but it conflicts with existing data. `409` is preferred for duplicate resource conflicts; `400` is simpler and widely used.

### 🎯 Interview Tip
Many candidates mix up 401 and 403. Nail this distinction — it's asked in nearly every backend interview. Also mention that FastAPI uses `status.HTTP_200_OK` constants (from Starlette) instead of magic numbers — shows production code awareness.

## 8. Validation Logic in Update Endpoints

### Core Concept Definition

Update endpoints need additional validation beyond schema validation — specifically checking that the new values don't violate **uniqueness constraints** or **referential integrity**.

### Common Validation Patterns

```python
@router.patch("/users/{user_id}")
async def update_user(user_id: int, user_data: UserUpdate, db: AsyncSession = Depends(get_db)):

    # 1. Check the resource to update exists
    result = await db.execute(select(User).where(User.id == user_id))
    user = result.scalar_one_or_none()
    if not user:
        raise HTTPException(status_code=404, detail="User not found")

    # 2. Check uniqueness constraints — only if the value actually changed
    if user_data.username is not None and user_data.username != user.username:
        existing = await db.execute(
            select(User).where(User.username == user_data.username)
        )
        if existing.scalar_one_or_none():
            raise HTTPException(status_code=400, detail="Username already taken")

    if user_data.email is not None and user_data.email != user.email:
        existing = await db.execute(
            select(User).where(User.email == user_data.email)
        )
        if existing.scalar_one_or_none():
            raise HTTPException(status_code=400, detail="Email already registered")

    # 3. Check referential integrity — only if foreign key is being changed
    # (e.g., if changing user_id on a post, verify new user exists)

    # 4. Apply updates
    update_data = user_data.model_dump(exclude_unset=True)
    for field, value in update_data.items():
        setattr(user, field, value)

    await db.commit()
    await db.refresh(user)
    return user
```

### Key Design Points

- **Check uniqueness only if the value changed** — avoids false positives when re-submitting the same username
- **Validate foreign keys before DB constraint fires** — gives a clean `400/404` instead of a cryptic `500`
- **Don't let DB constraint errors bubble up raw** — catch them and return meaningful HTTP errors

### 🎯 Interview Tip
Saying "I always check uniqueness constraints before attempting the write" shows awareness of the difference between *letting the DB fail and catching the exception* vs *proactively validating* — the latter gives better UX and cleaner error messages.

## 9. Computed/Property Fields in SQLAlchemy Models

### Core Concept Definition

A Python `@property` on a SQLAlchemy model creates a **computed attribute** — it's calculated on the fly from stored data, not persisted in the database. This keeps the DB lean while exposing convenient derived values to the API.

### Practical Code Example

```python
import os
from sqlalchemy.orm import DeclarativeBase, mapped_column, Mapped
from typing import Optional

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    username: Mapped[str] = mapped_column(unique=True)
    image_file: Mapped[Optional[str]] = mapped_column(default=None)
    # image_file stores only the filename: "corey.png"
    # NOT stored in DB: full path like "/media/profile_pics/corey.png"

    @property
    def image_path(self) -> str:
        """Compute full image path from stored filename."""
        if self.image_file:
            return f"/media/profile_pics/{self.image_file}"
        return "/static/profile_pics/default.jpeg"
```

### Why This Pattern Matters

- **Storage is minimal** — only the filename is stored, not the full path
- **Path logic lives in one place** — change the directory once in the property, not across the codebase
- **Works with Pydantic** — include `image_path` in the response schema to expose it via API
- **Extension-ready** — later you can add CDN URLs or signed URLs without changing the DB schema

### Common Interview Questions & Answers

❓ **"How do you return a computed value in a Pydantic response that isn't stored in the DB?"**
> Add a `@property` to the SQLAlchemy model that computes the value. Include the property name in the Pydantic response schema. With `from_attributes=True` (formerly `orm_mode`), Pydantic reads properties as if they were regular attributes.

### 🎯 Interview Tip
This pattern comes up in real-world scenarios like generating signed URLs for S3 objects, calculating `full_name` from `first_name + last_name`, or building dynamic paths. Knowing it and articulating the separation of concerns (store minimal data, compute the rest) is a strong signal.

## 10. Complete CRUD Design Pattern Summary

### The Full REST Pattern

| Operation | HTTP Method | Route | Success Code | Response |
|---|---|---|---|---|
| Create | POST | `/resources` | 201 | Created resource |
| Read all | GET | `/resources` | 200 | List of resources |
| Read one | GET | `/resources/{id}` | 200 | Single resource |
| Full update | PUT | `/resources/{id}` | 200 | Updated resource |
| Partial update | PATCH | `/resources/{id}` | 200 | Updated resource |
| Delete | DELETE | `/resources/{id}` | 204 | No content |

### Complete Pattern in FastAPI

```python
# schemas.py
class ResourceBase(BaseModel):
    title: str = Field(..., min_length=1, max_length=100)
    content: str

class ResourceCreate(ResourceBase):
    pass  # All required fields inherited from Base

class ResourceUpdate(BaseModel):
    title: Optional[str] = Field(None, min_length=1, max_length=100)
    content: Optional[str] = None  # All optional for PATCH

class ResourceResponse(ResourceBase):
    id: int
    created_at: datetime
    class Config:
        from_attributes = True

# router.py
@router.post("/resources", response_model=ResourceResponse, status_code=201)
@router.get("/resources", response_model=list[ResourceResponse])
@router.get("/resources/{id}", response_model=ResourceResponse)
@router.put("/resources/{id}", response_model=ResourceResponse)
@router.patch("/resources/{id}", response_model=ResourceResponse)
@router.delete("/resources/{id}", status_code=204)
```

### Schema Design Checklist

```
For any new resource, create these schemas:
  ✅ XxxBase        — shared fields with validators
  ✅ XxxCreate      — inherits Base, adds required-only fields (e.g., user_id)
  ✅ XxxUpdate      — all fields Optional[type] = None, no ownership fields
  ✅ XxxResponse    — inherits Base, adds id, timestamps, nested relations
```

## Quick Revision Cheat Sheet

```
PUT   → full replacement → use CreateSchema → update ALL fields
PATCH → partial update  → use UpdateSchema (all Optional) → exclude_unset=True

exclude_unset=True  →  only fields client sent  (PATCH must-have)
exclude_none=True   →  fields whose value is None  (different!)

setattr(obj, field, value)  →  dynamic field update in loop

DELETE → 204 No Content → no response_model → always check 404 first

cascade="all, delete-orphan"  →  on relationship, not column
  delete          →  children deleted when parent is deleted
  delete-orphan   →  children deleted when removed from collection

Status codes:
  200 → GET/PUT/PATCH success
  201 → POST success (resource created)
  204 → DELETE success (no body)
  400 → client error (duplicate, bad data)
  401 → not authenticated
  403 → authenticated, not authorized
  404 → resource not found
  422 → Pydantic validation error (FastAPI automatic)

@property on SQLAlchemy model → computed field, not stored in DB
  expose via Pydantic with from_attributes=True
```
