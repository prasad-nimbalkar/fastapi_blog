## 1. What are Path Parameters?

- Path parameters are **variable parts of a URL** that FastAPI captures and passes into your route function.
- Example: `/api/posts/1` → `1` is the path parameter (the post ID).
- FastAPI **automatically validates** path parameters based on the type hint in the function signature.

```
/api/posts/{post_id}
              ↑
        path parameter
```

> **Interview Tip:** Path parameters are defined using curly braces `{}` in the route path and matched as a function argument with the same name. FastAPI validates the type automatically.

---

## 2. Creating a Single Resource Endpoint

```python
@app.get("/api/posts/{post_id}")
def get_post(post_id: int):
    for post in posts:
        if post.get("id") == post_id:
            return post
    return {"error": "Post not found"}  # ❌ Wrong — see section 4
```

- `{post_id}` in the route captures the value from the URL.
- `post_id: int` in the function signature tells FastAPI to expect an integer.
- FastAPI passes the captured URL value directly into the function as an argument.

## 3. Type Validation with Type Hints

- FastAPI uses the **type hint** on the parameter to validate the incoming value automatically.
- If the value doesn't match the type → FastAPI returns a **422 Unprocessable Content** error with a detailed message.
- No extra validation code needed — it's built in.

```
/api/posts/hello  →  422 error: "input should be a valid integer"
/api/posts/1      →  200 OK (valid integer)
```

### What the 422 error looks like

```json
{
  "detail": [
    {
      "type": "int_parsing",
      "loc": ["path", "post_id"],
      "msg": "Input should be a valid integer, unable to parse string as an integer"
    }
  ]
}
```

> **Important:** This automatic validation is one of FastAPI's biggest advantages. You declare the expected type, FastAPI handles validation and returns structured error responses for free.

## 4. HTTP Exceptions & Proper Status Codes

### Why returning a plain error dict is wrong

```python
return {"error": "Post not found"}  # ❌ Returns 200 status code — misleading!
```

- Returning a plain dict always gives a **200 OK** response — even when the resource doesn't exist.
- API clients rely on HTTP status codes to know how to handle responses.
- A missing resource should return **404 Not Found**, not 200.

### Correct approach — raise HTTPException

```python
from fastapi import FastAPI, Request, HTTPException, status

@app.get("/api/posts/{post_id}")
def get_post(post_id: int):
    for post in posts:
        if post.get("id") == post_id:
            return post
    raise HTTPException(
        status_code=status.HTTP_404_NOT_FOUND,
        detail="Post not found"
    )
```

- `HTTPException` tells FastAPI to return a proper HTTP error response.
- `status_code` — use `status.HTTP_404_NOT_FOUND` instead of the raw number `404` for readability.
- `detail` — human-readable reason for the error, included in the response body.

### Common HTTP Status Codes

| Code | Constant | Meaning |
|---|---|---|
| 200 | `HTTP_200_OK` | Success |
| 404 | `HTTP_404_NOT_FOUND` | Resource not found |
| 422 | `HTTP_422_UNPROCESSABLE_ENTITY` | Validation error |
| 500 | `HTTP_500_INTERNAL_SERVER_ERROR` | Server error |

> **Interview Tip:** Always use `status.HTTP_XXX_NAME` constants instead of raw numbers — it makes code self-documenting, especially for less common codes like 422 or 409.

## 5. Template Route for Single Post

```python
@app.get("/posts/{post_id}", include_in_schema=False, name="post_page")
def post_page(request: Request, post_id: int):
    for post in posts:
        if post.get("id") == post_id:
            return templates.TemplateResponse(
                request,
                "post.html",
                {
                    "post": post,
                    "title": post["title"][:50]
                }
            )
    raise HTTPException(
        status_code=status.HTTP_404_NOT_FOUND,
        detail="Post not found"
    )
```

Key differences from the API route:
- Path is `/posts/{post_id}` (no `/api/` prefix) — this is the browser-facing page.
- Returns `TemplateResponse` instead of JSON.
- Context passes a **single `post`** (not a list) since we're displaying one post.
- `include_in_schema=False` — hides from API docs.
- `name="post_page"` — explicit name for `url_for()`.

## 6. Generating Links with `url_for()` and Path Parameters

- Pass path parameters as **keyword arguments** to `url_for()` in templates.

```html
<!-- home.html -->
<a href="{{ url_for('post_page', post_id=post.id) }}">
  {{ post.title }}
</a>
```

- `'post_page'` — the route name set by `name=` in the decorator.
- `post_id=post.id` — passes the path parameter value.
- FastAPI generates the correct URL: `/posts/1`, `/posts/2`, etc.

> **Interview Tip:** Using `url_for()` with named routes means if you ever change your URL structure (e.g. `/posts/` → `/blog/`), you only update it in one place — the route definition. All links update automatically.

## 7. Exception Handlers — API vs HTML Errors

### The problem

- API clients (JavaScript, mobile apps) expect **JSON error responses**.
- Browser users expect a **styled HTML error page**.
- One handler needs to serve both correctly based on the request path.

### Required imports

```python
from fastapi.responses import JSONResponse
from fastapi.exceptions import RequestValidationError
from starlette.exceptions import HTTPException as StarletteHTTPException
```

- `JSONResponse` — manually return a JSON response from the handler.
- `RequestValidationError` — catches 422 validation errors (separate from HTTPException).
- `StarletteHTTPException` — catches 404s raised by Starlette (e.g. route not found), not just FastAPI.

> **Important:** FastAPI is built on Starlette. When a user visits a route that doesn't exist at all (e.g. `/xyz`), **Starlette** raises the 404 — not FastAPI. You must catch `StarletteHTTPException` to handle those cases too.

### Exception handler for HTTP errors

```python
@app.exception_handler(StarletteHTTPException)
def http_exception_handler(request: Request, exc: StarletteHTTPException):
    message = exc.detail if exc.detail else "An error occurred. Please check your request and try again."

    if request.url.path.startswith("/api"):
        return JSONResponse(
            status_code=exc.status_code,
            content={"detail": message}
        )
    return templates.TemplateResponse(
        request,
        "error.html",
        {"status_code": exc.status_code, "message": message, "title": exc.status_code},
        status_code=exc.status_code
    )
```

- If URL starts with `/api` → return **JSON**.
- Otherwise → return **HTML error template**.
- Always pass `status_code=exc.status_code` to the `TemplateResponse` — otherwise the browser receives a 200 even though it's an error page.

## 8. Handling Validation Errors (422)

```python
@app.exception_handler(RequestValidationError)
def validation_exception_handler(request: Request, exc: RequestValidationError):
    if request.url.path.startswith("/api"):
        return JSONResponse(
            status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
            content={"detail": exc.errors()}
        )
    return templates.TemplateResponse(
        request,
        "error.html",
        {
            "status_code": 422,
            "message": "The request was invalid.",
            "title": 422
        },
        status_code=status.HTTP_422_UNPROCESSABLE_ENTITY
    )
```

Key differences from the HTTP exception handler:
- Catches `RequestValidationError` — a different exception type than `HTTPException`.
- `RequestValidationError` does **not** have a `.status_code` attribute — always use `422` directly.
- For API: return `exc.errors()` — the full validation detail list.
- For HTML: show a generic user-friendly message — don't expose technical validation details to browser users.

## 9. Common Interview Questions

**Q: What is a path parameter in FastAPI?**
> A path parameter is a variable embedded in the URL path, defined with curly braces (e.g. `{post_id}`). FastAPI captures the value and passes it to the route function. Type hints on the parameter enable automatic validation.

---

**Q: What happens if a path parameter fails type validation in FastAPI?**
> FastAPI automatically returns a 422 Unprocessable Content response with a detailed error message explaining what went wrong (e.g. "unable to parse string as an integer"). No custom validation code is needed.

---

**Q: Why should you raise `HTTPException` instead of returning an error dict?**
> Returning a dict always sends a 200 OK status code, which misleads API clients. `HTTPException` sends the correct HTTP status code (e.g. 404), which clients use to detect and handle errors appropriately. This follows REST API best practices.

---

**Q: What is the difference between `HTTPException` from FastAPI and `HTTPException` from Starlette?**
> FastAPI's `HTTPException` handles errors raised manually in your code. Starlette's `HTTPException` handles lower-level errors like routes that don't exist at all. Since FastAPI is built on Starlette, you should catch both in your exception handler to cover all cases.

---

**Q: How do you serve different error responses (JSON vs HTML) from one exception handler?**
> Check `request.url.path.startswith("/api")` in the handler. If it's an API route, return a `JSONResponse`. Otherwise, return a `TemplateResponse` with an error template.

---

**Q: Why must you pass `status_code` explicitly to `TemplateResponse` in an error handler?**
> Without it, the browser receives a 200 OK response even though an error page is displayed. Passing the correct status code ensures HTTP clients and browsers handle the response correctly.

---

**Q: What is `RequestValidationError` and when does it occur?**
> It's raised when a request fails FastAPI's input validation — for example, passing a string where an integer is expected. It's a separate exception type from `HTTPException` and must be caught with its own `@app.exception_handler(RequestValidationError)`.

## 10. Common Mistakes & Pitfalls

> **Pitfall:** Returning `{"error": "not found"}` instead of raising `HTTPException` — the client always gets a 200 OK, which is incorrect and breaks API contract.

> **Pitfall:** Only catching FastAPI's `HTTPException` in the exception handler — Starlette-level 404s (for non-existent routes) won't be caught, and users will see raw error responses.

> **Pitfall:** Forgetting to pass `status_code=exc.status_code` to `TemplateResponse` in error handlers — the browser displays the error page but gets a 200 response.

> **Pitfall:** Trying to access `.status_code` on `RequestValidationError` — it doesn't have that attribute. Always use `status.HTTP_422_UNPROCESSABLE_ENTITY` directly.

> **Pitfall:** Not giving template routes an explicit `name=` — `url_for()` can't generate the correct link without a unique route name.

> **Pitfall:** Forgetting `request: Request` as the first parameter in template routes — Jinja2 requires it.

---

## 11. Best Practices

- Always use `raise HTTPException(...)` for error responses — never return raw error dicts.
- Use `status.HTTP_XXX_NAME` constants instead of raw status code numbers.
- Separate API routes (`/api/...` → JSON) from page routes (`/posts/...` → HTML) clearly.
- Use a single exception handler that checks the request path to serve JSON or HTML errors.
- Catch both `StarletteHTTPException` and `RequestValidationError` for full error coverage.
- Use `url_for()` with named routes to generate links — never hardcode URLs in templates.
- Slice long strings (e.g. `title[:50]`) before passing to templates to avoid layout issues.
- Always pass `status_code` to `TemplateResponse` in error handlers.
