## 1. Why a Database?

| In-Memory List (before) | Database (after) |
|---|---|
| Data lost on server restart | Data persists across restarts |
| Manual ID generation | Auto-incremented IDs |
| Manual loop searches | SQL queries via SQLAlchemy |
| Not scalable | Scales to production |
| No relationships | Proper foreign keys & joins |

> **Interview Tip:** Always explain *why* a database is needed — persistence, scalability, relationships, and data integrity. Never just say "we need a database."

## 2. Architecture — Three Layers

```
┌─────────────────────────────────────────┐
│  1. Database Models (models.py)         │
│     SQLAlchemy classes — what we STORE  │
├─────────────────────────────────────────┤
│  2. Pydantic Schemas (schemas.py)       │
│     what we ACCEPT and RETURN via API   │
├─────────────────────────────────────────┤
│  3. API Routes (main.py)                │
│     FastAPI endpoints — handle requests │
└─────────────────────────────────────────┘
```

**Data flow:**
```
Request → Pydantic validates → SQLAlchemy stores/retrieves → Pydantic formats → Response
```

> **Important:** Database models and Pydantic schemas are **intentionally separate classes**. Mixing them reduces flexibility and control. Change one without breaking the other.

## 3. SQLAlchemy vs SQLModel

| | SQLAlchemy + Pydantic (separate) | SQLModel |
|---|---|---|
| Industry standard | ✅ Yes | ❌ Not yet |
| Seen in production codebases | ✅ Common | Less common |
| Full control | ✅ Yes | Partial |
| Single class for both | ❌ No | ✅ Yes |

> **Interview Tip:** SQLModel (by FastAPI's creator) combines both, but most real-world production codebases use separate SQLAlchemy models and Pydantic schemas. Understanding the separation makes you more hireable.

## 4. Installation & Database Choice

```bash
pip install sqlalchemy
```

- **SQLite** — built into Python, no server needed, great for development.
- **PostgreSQL** — production standard; switching from SQLite only requires changing the connection URL.
- SQLAlchemy makes this switch nearly seamless — same code, different URL.

## 5. database.py — Configuration

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, DeclarativeBase

DATABASE_URL = "sqlite:///./blog.db"

engine = create_engine(
    DATABASE_URL,
    connect_args={"check_same_thread": False}  # SQLite-specific
)

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

class Base(DeclarativeBase):
    pass

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

### Key components explained

| Component | Purpose |
|---|---|
| `DATABASE_URL` | Connection string — change this to switch databases |
| `engine` | The actual connection to the database |
| `check_same_thread=False` | SQLite only — allows multiple threads (FastAPI uses multiple threads) |
| `SessionLocal` | Factory that creates database sessions (one per request) |
| `autocommit=False` | We control when changes are saved |
| `autoflush=False` | We control when pending changes are sent to the DB |
| `Base` | All models inherit from this — SQLAlchemy v2 modern style |
| `get_db()` | Dependency function — provides a DB session, cleans up after the request |

> **Important:** `DeclarativeBase` is the **SQLAlchemy v2** way. The older v1 pattern was `declarative_base()` from `sqlalchemy.ext.declarative`. You will see both in real codebases.

> **Interview Tip:** `get_db()` uses Python's `yield` making it a **generator**. FastAPI's dependency injection runs the code before `yield` to set up the session and the code after `yield` (the `finally` block) to clean up — even if an error occurs.

## 6. models.py — Database Models

```python
from __future__ import annotations  # enables forward references on older Python versions
from datetime import datetime, UTC
from sqlalchemy import String, ForeignKey
from sqlalchemy.orm import Mapped, mapped_column, relationship
from database import Base

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    username: Mapped[str] = mapped_column(String, unique=True, nullable=False)
    email: Mapped[str] = mapped_column(String, unique=True, nullable=False)
    image_file: Mapped[str | None] = mapped_column(String, nullable=True)

    posts: Mapped[list[Post]] = relationship("Post", back_populates="author")

    @property
    def image_path(self) -> str:
        if self.image_file:
            return f"/media/profile_pictures/{self.image_file}"
        return "/static/profile_pictures/default.jpeg"
```

### Column options explained

| Option | Meaning |
|---|---|
| `primary_key=True` | Auto-increments the ID |
| `unique=True` | No duplicate values allowed |
| `nullable=False` | Field is required (cannot be NULL) |
| `index=True` | Speeds up queries filtering by this column |

> **Interview Tip:** `@property` on a model creates a computed attribute — not stored in the database, but readable like a normal field. With `from_attributes=True`, Pydantic can read these properties too.

## 7. Relationships — User & Post

```python
# User model — one side (one user has many posts)
posts: Mapped[list[Post]] = relationship("Post", back_populates="author")

# Post model — many side (many posts belong to one user)
class Post(Base):
    __tablename__ = "posts"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String, nullable=False)
    content: Mapped[str] = mapped_column(String, nullable=False)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"), index=True)
    date_posted: Mapped[datetime] = mapped_column(
        default=lambda: datetime.now(UTC)
    )

    author: Mapped[User] = relationship("User", back_populates="posts")
```

### Relationship concepts

| Concept | Explanation |
|---|---|
| `ForeignKey("users.id")` | Links posts to a specific user |
| `index=True` on FK | Speeds up queries filtering by `user_id` |
| `relationship()` | Lets you access related objects (`post.author`, `user.posts`) |
| `back_populates` | Links both sides of the relationship together |
| `lambda: datetime.now(UTC)` | Called at insert time — sets creation timestamp automatically |

> **Important:** Index foreign keys that you query frequently. Primary keys are indexed automatically; foreign keys are not.

> **Interview Tip:** `user.posts` returns all of a user's posts. `post.author` returns the full user object. SQLAlchemy handles the SQL JOIN automatically.

## 8. Updating Pydantic Schemas

### User schemas

```python
from pydantic import BaseModel, ConfigDict, Field, EmailStr
from datetime import datetime

class UserBase(BaseModel):
    username: str = Field(min_length=1, max_length=50)
    email: EmailStr = Field(max_length=120)  # validates proper email format

class UserCreate(UserBase):
    pass  # password field added later when auth is implemented

class UserResponse(UserBase):
    model_config = ConfigDict(from_attributes=True)
    id: int
    image_file: str | None
    image_path: str  # reads from @property on the User model
```

### Updated Post schemas

```python
class PostBase(BaseModel):
    title: str = Field(min_length=1, max_length=100)
    content: str = Field(min_length=1)
    # author removed — now comes from the User relationship

class PostCreate(PostBase):
    user_id: int  # temporary — replaced by auth session later

class PostResponse(PostBase):
    model_config = ConfigDict(from_attributes=True)
    id: int
    user_id: int
    date_posted: datetime      # datetime object — auto-serialized to ISO 8601
    author: UserResponse       # nested user object from the relationship
```

> **Important:** `author: UserResponse` in `PostResponse` means Pydantic reads `post.author` (the SQLAlchemy relationship), validates it as `UserResponse`, and includes the **full nested user data** in the API response automatically.

> **Interview Tip:** `EmailStr` from Pydantic validates proper email format automatically — no regex needed. Always use it for email fields.

## 9. Dependency Injection — get_db

```python
from typing import Annotated
from fastapi import Depends
from sqlalchemy.orm import Session
from database import get_db

# Reusable type alias for the DB session dependency
db_dependency = Annotated[Session, Depends(get_db)]

@app.post("/api/users", response_model=UserResponse, status_code=status.HTTP_201_CREATED)
def create_user(user: UserCreate, db: db_dependency):
    ...
```

- `Depends(get_db)` — tells FastAPI to call `get_db()` and inject the result as `db`.
- FastAPI handles session creation **and** cleanup automatically per request.
- Each request gets its **own isolated session** — safe for concurrent requests.

> **Interview Tip:** Dependency injection in FastAPI means "before running this function, call `get_db` and pass the result as `db`." You declare what you need; FastAPI provides it. This is cleaner than creating sessions inside each route.

## 10. Database CRUD Patterns in Routes

### SQLAlchemy v2 query style

```python
from sqlalchemy import select

# Get all posts
result = db.execute(select(models.Post))
posts = result.scalars().all()

# Get one post by ID
result = db.execute(select(models.Post).where(models.Post.id == post_id))
post = result.scalars().first()  # returns object or None
```

### Create pattern

```python
new_user = models.User(username=user.username, email=user.email)
db.add(new_user)      # stage the insert
db.commit()           # save to database
db.refresh(new_user)  # reload from DB (gets auto-generated ID etc.)
return new_user
```

### Check before create (avoid duplicate constraint errors)

```python
existing = db.execute(
    select(models.User).where(models.User.username == user.username)
).scalars().first()

if existing:
    raise HTTPException(status_code=status.HTTP_400_BAD_REQUEST, detail="Username already exists")
```

> **Important:** Always check for duplicates before inserting — gives a friendly error message instead of a raw database constraint violation error.

| Method | Purpose |
|---|---|
| `db.add(obj)` | Stages the object for insert |
| `db.commit()` | Executes and saves to the database |
| `db.refresh(obj)` | Reloads object from DB (gets server-generated values) |
| `.scalars().all()` | Returns a list of model objects |
| `.scalars().first()` | Returns one object or `None` |

> **Interview Tip:** `.scalars()` unwraps the SQLAlchemy row into the actual model object. Without it, you get a `Row` object, not your model instance.

## 11. Creating Tables on Startup

```python
# In main.py — runs once when the app starts
Base.metadata.create_all(bind=engine)
```

- Looks at all models inheriting from `Base` and creates tables that don't exist.
- **Idempotent** — safe to run multiple times; existing tables are not modified.
- Not suitable for production schema changes — use a migration tool like **Alembic** for that.

## 12. Serving User Uploads — Media Directory

```python
from fastapi.staticfiles import StaticFiles

app.mount("/static", StaticFiles(directory="static"), name="static")  # app files
app.mount("/media", StaticFiles(directory="media"), name="media")      # user uploads
```

| Directory | Purpose |
|---|---|
| `static/` | App files shipped with the code (CSS, JS, default images) |
| `media/` | User-uploaded content (profile pictures, attachments) |

- Keeping them separate is a production best practice — user uploads should not be committed to version control.
- Storing only the **filename** in the database (not the full path) decouples the database from the file structure.

## 13. Template Updates for Relationships

Since `author` is now a User object (not a string) and `date_posted` is a `datetime`:

```html
<!-- Author image — dynamic now -->
<img src="{{ post.author.image_path }}">

<!-- Author username — was post.author (string), now an object -->
{{ post.author.username }}

<!-- Link to user's posts page -->
<a href="{{ url_for('user_post', user_id=post.author.id) }}">
  {{ post.author.username }}
</a>

<!-- Format datetime in template — strftime works in Jinja2 -->
{{ post.date_posted.strftime("%B %d, %Y") }}
```

> **Interview Tip:** Format dates in templates, not in the API response. The API returns ISO 8601 (standard, machine-readable). The template formats it for humans. Same data, different presentations.

## 15. Common Interview Questions

**Q: What is an ORM and why use SQLAlchemy?**
> An ORM (Object-Relational Mapper) lets you interact with a database using Python objects instead of raw SQL. SQLAlchemy is the most popular Python ORM — it handles query generation, relationships, and connection management. It also lets you switch databases (SQLite → PostgreSQL) by changing only the connection URL.

---

**Q: What is the difference between SQLAlchemy models and Pydantic schemas?**
> SQLAlchemy models define database tables — what gets stored, column types, relationships. Pydantic schemas define the API contract — what data comes in and goes out. They are intentionally separate so you can change one without breaking the other.

---

**Q: What is dependency injection in FastAPI and how does `get_db` use it?**
> Dependency injection means declaring what a function needs and letting FastAPI provide it. `get_db()` is a generator function that creates a database session, yields it to the route, and closes it afterward in the `finally` block. FastAPI calls it automatically for every request that declares `db: Annotated[Session, Depends(get_db)]`.

---

**Q: What does `from_attributes=True` do in Pydantic?**
> It allows Pydantic to read data from SQLAlchemy model objects (using dot notation like `post.title`) in addition to plain dictionaries. Required for all response schemas that serialize ORM objects. Also reads `@property` attributes — not just database columns.

---

**Q: What is `Base.metadata.create_all(bind=engine)` and when should you use it?**
> It creates all database tables that don't already exist, based on models that inherit from `Base`. It's idempotent (safe to run multiple times). Fine for development but not for production schema migrations — use Alembic for that.

---

**Q: Why index foreign keys?**
> Primary keys are indexed automatically. Foreign keys are not. If you frequently query `posts` filtered by `user_id`, an index makes those queries much faster. The trade-off is slightly slower writes — almost always worth it for read-heavy tables.

---

**Q: Why store only the filename in the database instead of the full file path?**
> Decouples the database from the file system structure. If the folder hierarchy changes, you only update one place (the path logic in the model), not every row in the database.

---

**Q: What is the difference between `db.commit()` and `db.refresh()`?**
> `db.commit()` saves all staged changes to the database permanently. `db.refresh(obj)` reloads the object from the database after the commit — useful for getting server-generated values like auto-incremented IDs or default timestamps.

## 16. Common Mistakes & Pitfalls

> **Pitfall:** Forgetting `check_same_thread=False` for SQLite in FastAPI — SQLite by default only allows one thread, but FastAPI handles concurrent requests across threads.

> **Pitfall:** Using the old SQLAlchemy v1 `db.query(Model)` pattern instead of v2's `db.execute(select(Model))` — both work, but v2 style is the current standard.

> **Pitfall:** Forgetting `from_attributes=True` on response schemas — Pydantic will fail to serialize SQLAlchemy model objects.

> **Pitfall:** Not calling `db.refresh()` after `db.commit()` — auto-generated fields (ID, timestamp) may not be populated in the returned object.

> **Pitfall:** Catching only the database constraint error for duplicates instead of checking first — gives users an unhelpful raw database error message.

> **Pitfall:** Not indexing foreign keys — results in full table scans on common queries like "get all posts by user."

> **Pitfall:** Using `Base.metadata.create_all()` for production schema changes — it does not alter existing tables. Use Alembic migrations instead.

> **Pitfall:** Committing user-uploaded media to version control — keep `media/` in `.gitignore`.

---

## 17. Best Practices

- Keep `database.py`, `models.py`, `schemas.py`, and `main.py` in separate files — clear separation of concerns.
- Always use `get_db()` with dependency injection — never create sessions manually inside routes.
- Check for duplicates before inserting — gives friendly error messages and avoids raw DB errors.
- Index foreign keys that appear in frequent `WHERE` clauses.
- Store only filenames in the database, not full paths — decouple DB from file structure.
- Use `@property` on models for computed fields (like `image_path`) — keeps logic in one place.
- Store user-uploaded files in `media/`, ship-with-app files in `static/` — never mix them.
- Use `datetime` with timezone (`UTC`) for all timestamps — avoids timezone bugs in production.
- Format dates in templates or the frontend — let the API return standardized ISO 8601.
- Use SQLite for development, PostgreSQL for production — same SQLAlchemy code, different URL.
