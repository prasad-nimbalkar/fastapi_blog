## 1. API-Driven Frontend Architecture — The Core Pattern

### Core Concept Definition

An **API-driven frontend** separates the backend (data, validation, business logic via JSON API) from the frontend (presentation, user interaction via HTML/CSS/JS). The backend exposes a clean REST API; the frontend consumes it — as does any other client (mobile app, CLI tool, third-party integration).

### Interview-Relevant Details

- **Backend returns JSON** → the same API serves web, mobile, and desktop clients
- **Frontend sends JSON** → via `fetch()` with `Content-Type: application/json`
- The frontend never bypasses validation — it still hits the same API endpoints that a `curl` command or Postman request would use
- This is different from **server-rendered forms** (where the HTML form POSTs directly to the server and gets a new page back)

### The Architecture

```
Browser (HTML/CSS/JS)
    │
    │  JSON over HTTP (fetch API)
    ▼
FastAPI Backend (/api/posts, /api/users)
    │
    ▼
Database (SQLite / PostgreSQL)
```

### Common Interview Questions & Answers

❓ **"Why build a JSON API instead of rendering forms server-side?"**
> A JSON API decouples the backend from any specific client. The same endpoints serve a web frontend, a mobile app, a CLI tool, or third-party integrations. Server-rendered forms tightly couple the backend to one specific HTML UI.

❓ **"What are the trade-offs between a full SPA (React) and a hybrid approach?"**
> A full SPA offers rich interactivity but requires more infrastructure (separate deployment, CORS setup, client-side routing). A hybrid approach — HTML pages with modals and `fetch()` calls — is simpler to deploy, works without JavaScript frameworks, and still provides good UX for most CRUD apps. The backend API is identical in both cases.

### 🎯 Interview Tip
For data engineering roles at BFSI companies, the key point is: **your FastAPI backend doesn't care about the client**. Whether it's a React SPA, a Python script, or a Jinja2 template — it all talks to the same JSON API. This is the "reusable backend" argument interviewers want to hear.

## 2. JavaScript Fetch API — Calling FastAPI Endpoints

### Core Concept Definition

`fetch()` is the browser's built-in way to make HTTP requests from JavaScript. It's Promise-based and replaces the older `XMLHttpRequest`. Used to call REST API endpoints asynchronously without reloading the page.

### Standard Fetch Pattern for FastAPI

```javascript
// POST — Create a resource
const response = await fetch("/api/posts", {
    method: "POST",
    headers: {
        "Content-Type": "application/json"
        // Later: "Authorization": `Bearer ${token}`
    },
    body: JSON.stringify({
        title: "My Post",
        content: "Post content",
        user_id: 1
    })
});

if (response.ok) {
    const data = await response.json();  // Parse the JSON response
    console.log("Created:", data);
} else {
    const error = await response.json(); // FastAPI error details in JSON too
    console.error("Error:", error.detail);
}
```

```javascript
// PATCH — Partial update
const response = await fetch(`/api/posts/${postId}`, {
    method: "PATCH",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ title: "Updated Title" })  // Only changed fields
});

// DELETE — No body needed
const response = await fetch(`/api/posts/${postId}`, {
    method: "DELETE"
    // No body, no Content-Type header needed
});

if (response.status === 204) {
    // 204 No Content — success, nothing returned
    window.location.href = "/";  // Redirect since the resource is gone
}
```

### Key Points About fetch()

| Property | What It Does |
|---|---|
| `response.ok` | `true` for 2xx status codes (200–299) |
| `response.status` | Exact HTTP status code (200, 201, 204, 404, 422...) |
| `response.json()` | Parses response body as JSON (async — must be awaited) |
| `JSON.stringify()` | Converts JS object to JSON string for the request body |

### Common Interview Questions & Answers

❓ **"What is `response.ok` in the Fetch API?"**
> It's a boolean that is `true` when the HTTP status code is in the 2xx range (success). It's a convenient shorthand for checking `response.status >= 200 && response.status < 300`.

❓ **"Why do you need `Content-Type: application/json` in the headers?"**
> It tells the server that the request body is JSON. Without it, FastAPI may not parse the body correctly and will return a 422 validation error. FastAPI expects JSON for endpoint parameters defined as Pydantic models.

❓ **"Why doesn't a DELETE request need a body?"**
> The resource to delete is identified by the URL path (`/api/posts/{id}`). There's no data to send — the ID in the URL is sufficient. Adding a body to DELETE is technically allowed by HTTP spec but is non-standard and avoided in REST APIs.

### 🎯 Interview Tip
Mentioning that `response.status === 204` needs to be checked *separately* from `response.ok` for DELETE (because 204 is in the 2xx range, so `response.ok` is `true` — but you can't call `response.json()` on a 204 body) shows real-world fetch awareness.

## 3. Preventing Default Form Submission — `event.preventDefault()`

### Core Concept Definition

By default, when an HTML form is submitted, the browser sends a full-page HTTP POST request and navigates to a new URL. `event.preventDefault()` stops this, allowing JavaScript to handle the submission instead — calling the API, showing feedback, and controlling page behavior.

### Why It's Needed

```javascript
document.getElementById("create-post-form").addEventListener("submit", async (event) => {
    event.preventDefault();  // ← Stop browser from doing a full-page POST
    // Now we control everything:
    // 1. Gather form data
    // 2. Call the API with fetch()
    // 3. Show a modal for success or error
    // 4. Reload only specific parts of the page
});
```

```html
<!-- Without preventDefault: form POSTs to /action and reloads the page -->
<form action="/submit" method="POST">...</form>

<!-- With preventDefault + fetch: stays on page, handles response in JS -->
<form id="create-post-form">  <!-- No action or method attribute -->
    ...
</form>
```

### Interview-Relevant Details

- Forms without `action` attributes submit to the current URL — `preventDefault` is essential
- This pattern enables **inline feedback** (modals, error messages) without page navigation
- The same pattern is used in React (`onSubmit={e => { e.preventDefault(); ... }}`) and Vue

### Common Interview Questions & Answers

❓ **"What does `event.preventDefault()` do in form handling?"**
> It cancels the browser's default behavior — in this case, the full-page form submission and navigation. This lets JavaScript intercept the submit event, call the API using `fetch()`, and handle the response without leaving the current page.

## 4. FormData and Serialization

### Core Concept Definition

`FormData` is a browser API that automatically collects all values from an HTML form. `Object.fromEntries()` converts it to a plain JavaScript object that can be serialized to JSON with `JSON.stringify()`.

### The Pattern

```javascript
const form = document.getElementById("create-post-form");

form.addEventListener("submit", async (event) => {
    event.preventDefault();

    // 1. Collect form inputs automatically
    const formData = new FormData(form);

    // 2. Convert to plain JS object
    // FormData: { title: "My Post", content: "Content here" }
    const postData = Object.fromEntries(formData.entries());
    // postData = { title: "My Post", content: "Content here" }

    // 3. Add fields not in the form (e.g., user_id from auth token later)
    postData.user_id = 1;  // Temporary — will come from JWT token

    // 4. Remove fields that shouldn't go in the body (e.g., hidden IDs for URL)
    const { post_id, ...bodyData } = postData;  // post_id goes in URL, not body

    // 5. Send as JSON
    await fetch("/api/posts", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify(bodyData)
    });
});
```

### Common Interview Questions & Answers

❓ **"How do you send form data to a FastAPI endpoint as JSON?"**
> Use `new FormData(form)` to collect the form values, `Object.fromEntries()` to convert to a plain object, add any additional fields (like auth data), and send it with `fetch()` using `JSON.stringify()` as the body and `Content-Type: application/json` as the header.

## 5. Handling FastAPI Validation Error Responses

### Core Concept Definition

FastAPI returns **two different shapes** for error `detail`:
- A **string** for custom errors: `{"detail": "Post not found"}`
- An **array of objects** for Pydantic validation errors: `{"detail": [{"loc": [...], "msg": "...", "type": "..."}]}`

Frontend code must handle both shapes — otherwise raw JSON arrays leak into the UI.

### FastAPI Error Response Shapes

```json
// Custom HTTPException — detail is a string
{
    "detail": "Post not found"
}

// Pydantic validation error (422) — detail is a list
{
    "detail": [
        {
            "loc": ["body", "title"],
            "msg": "String should have at most 100 characters",
            "type": "string_too_long"
        },
        {
            "loc": ["body", "content"],
            "msg": "Field required",
            "type": "missing"
        }
    ]
}
```

### Utility Function to Handle Both

```javascript
function getErrorMessage(data) {
    if (!data.detail) return "An unexpected error occurred";

    // String error — custom HTTPException
    if (typeof data.detail === "string") {
        return data.detail;
    }

    // Array of validation errors — Pydantic 422
    if (Array.isArray(data.detail)) {
        return data.detail
            .map(err => err.msg)        // Extract the human-readable message
            .join(", ");                // Join multiple errors
    }

    return "An unexpected error occurred";
}

// Usage
const errorData = await response.json();
const message = getErrorMessage(errorData);
// → "String should have at most 100 characters, Field required"
```

### Common Interview Questions & Answers

❓ **"What shape does FastAPI return for validation errors?"**
> FastAPI returns a 422 status with a JSON body where `detail` is a list of error objects. Each object has a `loc` (location — which field failed), `msg` (human-readable message), and `type` (error type). Custom `HTTPException` errors have `detail` as a plain string. Frontend code must handle both.

❓ **"What HTTP status code does FastAPI return for Pydantic validation failures?"**
> `422 Unprocessable Entity`. This is automatic — FastAPI validates request bodies against Pydantic schemas and returns 422 with the validation errors if any field fails. You don't need to write this logic yourself.

### 🎯 Interview Tip
For your JIRA automation pipeline and Anthropic API work — knowing that `detail` can be either a string or list is directly relevant to building robust error handling in any API client code you write. This exact pattern applies to any FastAPI service you consume.

## 6. HTTP Method Selection — POST vs PATCH vs DELETE

### Core Concept Definition

Choosing the right HTTP method is a core REST API design skill. For frontend integration, the method determines what the server expects and how it behaves.

### Method Decision in the Frontend

```javascript
// POST — Create a new resource (body contains all required fields)
fetch("/api/posts", {
    method: "POST",
    body: JSON.stringify({ title, content, user_id })
})

// PATCH — Partial update (body contains only changed fields)
fetch(`/api/posts/${postId}`, {
    method: "PATCH",
    body: JSON.stringify({ title, content })
    // user_id not included — not changing ownership
})

// DELETE — Remove resource (no body, ID in URL)
fetch(`/api/posts/${postId}`, {
    method: "DELETE"
    // No body needed
})
```

### Why PATCH for the Edit Form

```javascript
// The edit form sends title + content but NOT user_id
// → This is a partial update → PATCH is semantically correct

const updateData = Object.fromEntries(new FormData(editForm).entries());
// updateData = { post_id: "5", title: "New Title", content: "New Content" }

// Remove post_id from body — it goes in the URL, not the body
delete updateData.post_id;  // or use destructuring

fetch(`/api/posts/${postId}`, {
    method: "PATCH",              // Partial update
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(updateData)  // Only title + content
})
```

## 7. Server-Side Ordering with ORDER BY

### Core Concept Definition

When displaying lists (posts, comments, items), the order should be controlled by the **backend**, not sorted after the fact in JavaScript. Database-level `ORDER BY` is more efficient, consistent across all clients, and enforces a single source of truth.

> **Rule:** Business logic — including sort order — belongs in the backend.

### The Problem and Fix

```python
# ❌ WRONG — default order (insertion order, oldest first)
result = await db.execute(select(Post))
posts = result.scalars().all()

# ✅ CORRECT — explicit descending order (newest first)
from sqlalchemy import desc

result = await db.execute(
    select(Post)
    .options(selectinload(Post.author))
    .order_by(desc(Post.date_posted))   # Newest first
)
posts = result.scalars().all()

# Alternative SQLAlchemy syntax:
.order_by(Post.date_posted.desc())      # Same result, ORM-style
```

### Where to Apply ORDER BY

Apply `order_by` to **every query that returns a list** — not just one route:

```python
# Apply consistently to ALL list-returning queries:
# 1. GET /api/posts                 → list of all posts
# 2. GET /                          → homepage posts (template route)
# 3. GET /users/{id}/posts          → user's posts page
# 4. GET /api/users/{id}/posts      → user's posts API
```

### Common Interview Questions & Answers

❓ **"Should sorting be done in the frontend (JavaScript) or backend (SQL)?"**
> Always in the backend with `ORDER BY`. Database-level sorting is executed by the DB engine's optimized sort algorithms (which use indexes), operates on the full dataset before pagination, is consistent across all clients, and doesn't transfer unsorted data across the network just to sort it in the browser.

❓ **"What is the difference between ascending and descending order in SQLAlchemy?"**
> By default, `order_by(Post.date_posted)` is ascending (oldest first). Add `.desc()` or wrap with `desc()` for descending (newest first): `order_by(Post.date_posted.desc())` or `order_by(desc(Post.date_posted))`.

❓ **"How do you find all queries in a codebase that need an ORDER BY added?"**
> Search for `db.execute` or `select(ModelName)` across the project. Any query returning a list (identified by `scalars().all()` or matching a `list[ResponseSchema]` return type) is a candidate. This is also a good argument for abstracting queries into a repository/service layer — you change the ordering in one place.

### 🎯 Interview Tip
Mentioning **indexes on sort columns** is a strong bonus: *"In production, I'd also add a database index on `date_posted` since it's used in ORDER BY — without an index, every list query would do a full table scan as the dataset grows."* This is directly relevant to your data engineering background.

## 8. Separation of Concerns — Backend vs Frontend Responsibilities

### Core Concept Definition

In an API-driven architecture, responsibilities are cleanly divided between backend and frontend. The backend is the **single source of truth** for data integrity, business rules, and validation.

### Responsibility Matrix

| Concern | Where It Lives | Why |
|---|---|---|
| Data validation | **Backend (Pydantic)** | Can't trust client input; all clients share the same rules |
| Business logic | **Backend** | Consistent across all clients (web, mobile, CLI) |
| Sort order / filtering | **Backend (SQL)** | Efficient, consistent, prevents inconsistent results |
| Authentication / authorization | **Backend** | Security must not be client-side |
| Presentation / UI | **Frontend** | Only the browser cares about modals, colors, layout |
| User interaction | **Frontend** | Form submission, click handlers, page transitions |
| Error display | **Frontend** | Converts API error JSON into human-readable UI |

### Why This Matters

```javascript
// ❌ Trusting the frontend for security:
// Anyone can call the API directly bypassing the UI
fetch("/api/posts/5", {
    method: "DELETE",
    body: JSON.stringify({ user_id: 1 })  // Claiming to be user 1 — not verified!
})

// ✅ Backend must verify ownership regardless of what the frontend sends:
@router.delete("/{post_id}")
async def delete_post(post_id: int, current_user: User = Depends(get_current_user)):
    post = await get_post_or_404(post_id, db)
    if post.user_id != current_user.id:  # Server-side check — can't be bypassed
        raise HTTPException(status_code=403, detail="Not authorized")
    await db.delete(post)
```

### Common Interview Questions & Answers

❓ **"Can you validate data on the frontend to avoid hitting the backend?"**
> Frontend validation improves UX (immediate feedback, no round-trip), but it never replaces backend validation. The API must validate everything — a malicious client can bypass the UI entirely and call the API directly with invalid data. Always validate in both places.

❓ **"Why is sort order a backend concern?"**
> Because any client (mobile app, API consumer, CLI tool) that uses the same API should get data in the same order. If sorting is in the frontend, a mobile app using the same API might display posts in a different order — inconsistent behavior from the same data source.

### 🎯 Interview Tip
For Senior Data Engineer interviews, this translates directly: data transformations and sorting in a pipeline should happen at the data layer (SQL, Spark), not in downstream Python scripts that process the results. The same principle applies.

## 9. Security Scaffolding — Temporary Hard-coded Values

### Core Concept Definition

During development, **temporary scaffolding** (like a hard-coded `user_id = 1`) allows you to build and test functionality before the full authentication system is in place. This is a common, intentional development pattern — not a mistake — as long as it's clearly marked and replaced before production.

### The Scaffolding Pattern

```javascript
// TEMPORARY — Replace with JWT token data when auth is added
const postData = Object.fromEntries(formData.entries());
postData.user_id = 1;  // ← Hard-coded for now; will come from token

fetch("/api/posts", {
    method: "POST",
    headers: {
        "Content-Type": "application/json",
        // Future: "Authorization": `Bearer ${localStorage.getItem("token")}`
    },
    body: JSON.stringify(postData)
});
```

```python
# TEMPORARY — Replace with Depends(get_current_user) when auth is added
@router.delete("/{post_id}", status_code=204)
async def delete_post(post_id: int, db: AsyncSession = Depends(get_db)):
    # Future: verify post.user_id == current_user.id before allowing deletion
    ...
```

### What Changes When Auth Is Added

| Now (Scaffolding) | After Authentication |
|---|---|
| `user_id` hard-coded in JS | `user_id` extracted from JWT token |
| Any user can delete any post | Only the post's author can delete it |
| "Create Post" button always visible | Button only visible when logged in |
| No `Authorization` header | `Bearer {token}` in every request header |
| Ownership check: `post.user_id == 1` | Ownership check: `post.user_id == current_user.id` |

### Common Interview Questions & Answers

❓ **"How do you handle features that depend on auth before auth is implemented?"**
> Use temporary scaffolding — hard-code a user ID or bypass auth checks with a clear comment marking it as temporary. This lets the team build and test the feature independently. The scaffolding is replaced when the auth system is ready, following a clear contract defined upfront.

## 10. Shared JavaScript Utilities — DRY Principle

### Core Concept Definition

The **DRY (Don't Repeat Yourself)** principle applies to JavaScript just as it does to Python. Common operations used across multiple pages (error parsing, modal management) belong in a shared utility module — imported where needed.

### Utility Module Pattern

```javascript
// static/js/utils.js — Shared across all pages

/**
 * Extracts a user-friendly error message from FastAPI's response.
 * Handles both string errors and Pydantic validation error arrays.
 */
export function getErrorMessage(data) {
    if (!data.detail) return "An unexpected error occurred";
    if (typeof data.detail === "string") return data.detail;
    if (Array.isArray(data.detail)) {
        return data.detail.map(err => err.msg).join(", ");
    }
    return "An unexpected error occurred";
}

/** Shows a Bootstrap modal by its DOM ID */
export function showModal(modalId) {
    const modalEl = document.getElementById(modalId);
    const modal = bootstrap.Modal.getOrCreateInstance(modalEl);
    modal.show();
}

/** Hides a Bootstrap modal by its DOM ID */
export function hideModal(modalId) {
    const modalEl = document.getElementById(modalId);
    const modal = bootstrap.Modal.getInstance(modalEl);
    if (modal) modal.hide();
}
```

```javascript
// In any page template — import only what's needed
import { getErrorMessage, showModal, hideModal } from "/static/js/utils.js";

form.addEventListener("submit", async (event) => {
    event.preventDefault();
    // ...fetch call...
    if (response.ok) {
        showModal("success-modal");
    } else {
        const data = await response.json();
        document.getElementById("error-message").textContent = getErrorMessage(data);
        showModal("error-modal");
    }
});
```

### Interview-Relevant Details

- Uses **ES Modules** (`type="module"` on `<script>`, `export`/`import`)
- ES Modules are scoped — variables don't leak to global scope
- The `type="module"` attribute also defers script loading automatically
- In Python terms: this is like creating a shared `utils.py` module imported across multiple files

## 11. Hybrid Rendering Architecture

### Core Concept Definition

A **hybrid rendering** approach combines server-rendered HTML pages (for initial page load) with JavaScript `fetch()` calls (for interactive CRUD operations). It's a pragmatic middle ground between full server-rendered apps and full SPAs.

### Architecture Comparison

| Approach | Pros | Cons |
|---|---|---|
| **Full server-render** | Simple, no JS required, SEO-friendly | Full page reload on every action, poor UX |
| **Full SPA (React/Vue)** | Richest interactivity, no page reloads | Complex setup, CORS needed, separate deployment |
| **Hybrid (this approach)** | Good UX via modals, reusable API, simple deployment | Page reloads after actions, more code than pure server-render |

### The Hybrid Pattern

```
Initial Load:     FastAPI returns full HTML page (Jinja2 template)
User Action:      JavaScript intercepts, calls JSON API via fetch()
Success:          Show modal, then reload page to reflect changes
Error:            Show error modal, user stays on current page
```

### Benefits of This Approach

- **No CORS complexity** — frontend and API served from same origin
- **No separate deployment** — one FastAPI process serves both HTML and API
- **Progressive enhancement** — works as a foundation; can migrate to React later
- **Reusable API** — mobile app can use the exact same endpoints immediately
- **Simpler state management** — page reload is the state refresh (no Redux/Zustand needed)

### Common Interview Questions & Answers

❓ **"When would you choose a hybrid approach over a full React SPA?"**
> For internal tools, admin dashboards, or MVPs where development speed matters more than rich interactivity. The hybrid approach deploys faster (one service), avoids CORS setup, and still gives a good user experience via modals. The API layer is already clean if we need to migrate to a SPA later.

```
  Always server-side (SQL) — never client-side (JS sort)

  Backend  → validation, business logic, auth, sort order, data integrity

```
