## 1. Authentication vs Authorization — Core Difference

| Concept | Question it answers | Example |
|---|---|---|
| **Authentication** | *Who are you?* | Logging in, verifying a JWT token |
| **Authorization** | *What are you allowed to do?* | Can this user edit THIS post? |

> **Important:** Authentication must happen before authorization. You can't check what someone is allowed to do if you don't know who they are first.

> 🎯 **Interview Tip:** Always distinguish these two clearly. A common interview mistake is conflating them. Authentication = identity. Authorization = permission.

### Before this tutorial (the problem)

- Routes had no protection — anyone could create, edit, or delete any resource.
- `PostCreate` schema accepted a `user_id` from the request body — any client could claim to be any user.
- Hard-coded `user_id = 1` was used everywhere on the frontend.

### After this tutorial (the fix)

- Routes are protected by the `get_current_user` dependency.
- `user_id` comes from the trusted JWT token — not the request body.
- Ownership checks prevent users from editing/deleting others' content.

## 2. The `get_current_user` Dependency

### What it does

A reusable FastAPI dependency that:
1. Extracts the JWT token from the `Authorization` header.
2. Verifies the token and extracts the `user_id`.
3. Queries the database for the actual `User` object.
4. Returns the user — or raises `401 Unauthorized` if anything fails.

```python
# auth.py
from typing import Annotated
from fastapi import Depends, HTTPException, status
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession
from database import get_db
import models

async def get_current_user(
    token: str = Depends(oauth2_scheme),   # extracts token from Authorization header
    db: AsyncSession = Depends(get_db)
):
    # Step 1: Verify the token
    user_id = verify_access_token(token)   # returns user_id string or None
    if user_id is None:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Not authenticated"
        )

    # Step 2: Convert user_id to int (stored as string in JWT)
    try:
        user_id = int(user_id)
    except ValueError:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Invalid token")

    # Step 3: Fetch the actual user from the database
    result = await db.execute(select(models.User).where(models.User.id == user_id))
    user = result.scalars().first()

    if user is None:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="User not found")

    return user  # full User object — available in any route that uses this dependency
```

### Key design decisions

| Decision | Reason |
|---|---|
| Returns full `User` object | Routes get everything they need — no extra DB query |
| Raises `401` (not `404`) if user not found | Don't confirm whether a user exists to unauthenticated callers |
| Converts `user_id` to `int` | JWTs store values as strings; DB needs an integer |
| Separate from `/me` endpoint | This is an internal dependency; `/me` is a public API endpoint |

> **Important:** The `get_current_user` dependency is NOT an endpoint — it's a helper that other routes use internally. The `/me` endpoint is what users call directly.

## 3. Type Alias with `Annotated` — `CurrentUser`

```python
# Reusable type alias — cleaner route signatures
CurrentUser = Annotated[models.User, Depends(get_current_user)]
```

### Without type alias (verbose)

```python
async def create_post(
    post: PostCreate,
    current_user: Annotated[models.User, Depends(get_current_user)],
    db: db_dependency
):
```

### With type alias (clean)

```python
async def create_post(
    post: PostCreate,
    current_user: CurrentUser,   # ← clean and reusable
    db: db_dependency
):
```

> 🎯 **Interview Tip:** `Annotated[Type, metadata]` is Python's way of attaching extra information to a type hint. FastAPI reads the `Depends(...)` metadata to know it should call `get_current_user` and inject the result. This pattern is common in modern FastAPI codebases.

### How `Annotated` works

```python
Annotated[models.User, Depends(get_current_user)]
# ↑ Type          ↑ Metadata FastAPI reads
# "This is a User object, obtained by calling get_current_user"
```

## 4. Removing User ID from Request Body

### Before — insecure

```python
class PostCreate(PostBase):
    user_id: int   # ❌ client can claim to be any user
```

### After — secure

```python
class PostCreate(PostBase):
    pass   # ✅ only title and content — user_id comes from the token
```

### In the route

```python
async def create_post(post: PostCreate, current_user: CurrentUser, db: db_dependency):
    new_post = models.Post(
        title=post.title,
        content=post.content,
        user_id=current_user.id   # ← from trusted JWT token, not request body
    )
```

> **Important:** Never trust client-supplied identity data. The server issues the JWT — only the server knows who it belongs to. Always get the user identity from the verified token.

## 5. Protecting Routes — Adding the Dependency

Just add `current_user: CurrentUser` to the function signature — that's it.

```python
@router.post("/api/posts", response_model=PostResponse, status_code=status.HTTP_201_CREATED)
async def create_post(
    post: PostCreate,
    current_user: CurrentUser,    # ← adding this line protects the route
    db: db_dependency
):
    # If no valid token → 401 is raised automatically before this line runs
    new_post = models.Post(
        title=post.title,
        content=post.content,
        user_id=current_user.id
    )
    db.add(new_post)
    await db.commit()
    await db.refresh(new_post, attribute_names=["author"])
    return new_post
```

### What happens without a valid token

```
Client sends request with no/invalid token
              ↓
FastAPI calls get_current_user (via Depends)
              ↓
verify_access_token returns None
              ↓
401 Unauthorized raised immediately
              ↓
Route function never runs
```

> 🎯 **Interview Tip:** FastAPI's dependency system handles auth rejection before the route logic executes. This is clean, reusable, and follows the **single responsibility principle** — routes focus on business logic, not auth checking.

## 6. Ownership Checks — 401 vs 403

### Adding an ownership check

```python
@router.put("/api/posts/{post_id}", response_model=PostResponse)
async def update_post(
    post_id: int,
    post_data: PostCreate,
    current_user: CurrentUser,
    db: db_dependency
):
    # Step 1: Check post exists
    result = await db.execute(select(models.Post).where(models.Post.id == post_id))
    post = result.scalars().first()
    if not post:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Post not found")

    # Step 2: Ownership check — does this user own this post?
    if post.user_id != current_user.id:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="Not authorized to update this post"
        )

    # Step 3: Perform update
    post.title = post_data.title
    post.content = post_data.content
    await db.commit()
    await db.refresh(post)
    return post
```

### 401 vs 403 — Critical difference

| Code | Name | Meaning | When to use |
|---|---|---|---|
| `401` | Unauthorized | Not authenticated — missing or invalid token | No token, expired token, invalid token |
| `403` | Forbidden | Authenticated but not permitted | Valid token, wrong user (doesn't own resource) |

> **Important:** Using 401 vs 403 correctly matters for API clients. A 401 tells the client "please log in." A 403 tells the client "you're logged in but you can't do this." They trigger different client-side behavior.

> ❓ **Common Question:** *"What is the difference between 401 and 403?"*
> 401 = not authenticated (who are you?). 403 = authenticated but forbidden (I know who you are, but no).

### Apply ownership checks to all mutation routes

```
Create Post  → user_id from token (no ownership check needed — you own what you create)
Update Post  → check post.user_id == current_user.id → 403 if mismatch
Delete Post  → check post.user_id == current_user.id → 403 if mismatch
Update User  → check user.id == current_user.id      → 403 if mismatch
Delete User  → check user.id == current_user.id      → 403 if mismatch
```

## 7. Reusing Dependencies — Simplifying `/me` Endpoint

### Before — manual, repetitive code (~30 lines)

```python
@router.get("/api/users/me")
async def get_me(token: str = Depends(oauth2_scheme), db: db_dependency):
    # manually extract token
    # manually verify token
    # manually convert user_id
    # manually query database
    # manually handle all errors
    ...
```

### After — with `CurrentUser` dependency (3 lines)

```python
@router.get("/api/users/me", response_model=UserResponse)
async def get_me(current_user: CurrentUser):
    return current_user   # dependency does all the work
```

> 🎯 **Interview Tip:** This is a textbook example of **DRY (Don't Repeat Yourself)** and **dependency injection** benefits. The same auth logic is reused across dozens of routes without duplication. If the token format changes, you update `get_current_user` once — everything else works.

## 8. Server-Side vs Client-Side Security

### The `/account` page — why it's not protected server-side

```python
@app.get("/account", include_in_schema=False)
async def account_page(request: Request):
    return templates.TemplateResponse(request, "account.html", {"title": "Account"})
    # No current_user dependency here — JWT is in localStorage, not sent with page requests
```

### Why JWT can't protect template routes directly

- JWT is stored in `localStorage` — only accessible by JavaScript in the browser.
- When a browser navigates to `/account`, it sends a normal GET request — no `Authorization` header.
- The server has no way to read `localStorage`.

### Two-layer security model

| Layer | Who enforces it | What it does |
|---|---|---|
| **Frontend (JS)** | Browser JavaScript | Checks `localStorage` for token; redirects to login if missing — UX convenience |
| **Backend (API)** | FastAPI dependencies | Validates token on every mutation endpoint; returns 401 if invalid — real security |

> **Important:** Client-side auth guards (JavaScript redirects) are for **user experience**, not security. A user could disable JavaScript and view the HTML. Real security lives in the API endpoints. The API always validates the token on write operations.

> 🎯 **Interview Tip:** Always distinguish between "UX-level protection" (frontend redirect) and "real security" (backend token validation). Saying this in an interview shows maturity in security thinking.

## 9. Frontend Integration — Authorization Headers

### Sending the JWT with API requests

```javascript
const token = getToken();  // retrieve from localStorage

// Token check before making the request
if (!token) {
    window.location.href = "/login";
    return;
}

const response = await fetch("/api/posts", {
    method: "POST",
    headers: {
        "Content-Type": "application/json",
        "Authorization": `Bearer ${token}`   // ← JWT sent here
    },
    body: JSON.stringify({ title, content })
});

// Handle auth errors from the server
if (response.status === 401) {
    window.location.href = "/login";   // token expired or invalid
    return;
}
if (response.status === 403) {
    showError("You are not authorized to perform this action.");
    return;
}
```

### Frontend auth error handling pattern

| Status code received | Frontend action |
|---|---|
| `401 Unauthorized` | Redirect to `/login` — token expired or missing |
| `403 Forbidden` | Show error message — user logged in but doesn't own resource |
| `2xx` | Proceed normally |

> **Important:** Always handle both 401 and 403 in frontend code — they require different UX responses. 401 → send them to login. 403 → show a "not allowed" message (they're already logged in).

## 10. Account Page & Delete Account Pattern

### Account page flow

```
Page loads → JS calls GET /api/users/me with token
           → populates form fields with user data
           → if no valid token → redirect to /login (UX guard)

Update profile → PATCH /api/users/{id} with Authorization header
              → server validates token + ownership → 403 if mismatch
              → on success → clear user cache, refresh navbar

Delete account → DELETE /api/users/{id} with Authorization header
              → server validates token + ownership
              → cascade deletes all user's posts (set up in models)
              → client clears token from localStorage → redirect to home
```

### After delete — client-side cleanup

```javascript
// After successful account deletion
localStorage.removeItem("access_token");   // clear the token
window.location.href = "/";                // redirect home
```

> **Interview Tip:** After deleting an account, always clear the token client-side. If the token isn't cleared, the client might try to use an expired token for subsequent requests.

## 11. Common Interview Questions

**Q: What is the difference between authentication and authorization?**
> Authentication answers "Who are you?" — it verifies identity through credentials like a JWT token. Authorization answers "What are you allowed to do?" — it checks if the authenticated user has permission for a specific action. Authentication always happens first.

---

**Q: How do you protect a FastAPI route to require a logged-in user?**
> Add a dependency parameter using `Depends(get_current_user)` to the route function. FastAPI calls the dependency before the route runs. If the token is missing or invalid, the dependency raises a `401 Unauthorized` and the route never executes.

---

**Q: What is the difference between a 401 and 403 HTTP status code?**
> 401 (Unauthorized) means the request lacks valid authentication — the user is not logged in or the token is invalid. 403 (Forbidden) means the user is authenticated but doesn't have permission for that specific action — like trying to delete someone else's post.

---

**Q: Why should `user_id` not be in the request body when creating a post?**
> If `user_id` is in the request body, any client can claim to be any user by sending a different ID. The user's identity should always come from the server-verified JWT token — not from client-supplied data. The server issued the token and knows who it belongs to.

---

**Q: What is a reusable dependency in FastAPI and why is it useful?**
> A reusable dependency is a function injected into multiple routes via `Depends()`. For auth, `get_current_user` extracts and validates the JWT, fetches the user from the DB, and returns it — or raises 401. Any route that needs auth just adds `current_user: CurrentUser` to its signature. This avoids repeating auth logic across every route (DRY principle).

---

**Q: Why can't you protect Jinja2 template routes with JWT the same way you protect API routes?**
> JWTs are stored in `localStorage`, which is only accessible by JavaScript. When a browser navigates to a page route, it sends a plain GET request without an `Authorization` header — the server can't read `localStorage`. Template routes use JavaScript to check the token and redirect if not logged in (UX guard), but the real security is enforced by the API endpoints that require the `Authorization` header.

---

**Q: What is `Annotated` and how is it used with FastAPI dependencies?**
> `Annotated[Type, metadata]` is Python's way to attach extra information to a type hint. FastAPI reads `Depends(...)` in the metadata to know it should call that dependency and inject the result. `CurrentUser = Annotated[models.User, Depends(get_current_user)]` creates a clean reusable alias used across route signatures.

## 12. Common Mistakes & Pitfalls

> **Pitfall:** Trusting `user_id` from the request body — clients can forge it. Always get user identity from the verified token.

> **Pitfall:** Using 401 for ownership failures — 401 means "not logged in." If the user is logged in but doesn't own the resource, use 403.

> **Pitfall:** Relying only on frontend JavaScript for security — JS-based redirects are UX conveniences. A user can bypass them by disabling JavaScript or using tools like Postman. The API must always validate the token server-side.

> **Pitfall:** Forgetting to handle 403 separately from 401 on the frontend — both need different UX responses. 401 redirects to login; 403 shows a "not allowed" message.

> **Pitfall:** Not clearing the JWT from `localStorage` after account deletion — the stale token could cause confusing behavior on subsequent requests.

> **Pitfall:** Returning 404 when a user is not found during token verification — this reveals whether a user exists to unauthenticated callers. Always return 401 for any token validation failure.

> **Pitfall:** Duplicating auth logic in every route instead of using a shared dependency — if the token format changes, you'd have to update every route. Use a single `get_current_user` dependency.

> **Pitfall:** Not converting `user_id` from string to int — JWTs store all claims as strings; SQLAlchemy expects an integer for the `id` column.

---

## 13. Best Practices

- Create a single reusable `get_current_user` dependency — import it everywhere instead of duplicating logic.
- Use `Annotated` type aliases (`CurrentUser`) to keep route signatures clean and readable.
- Never accept `user_id` in the request body for resources owned by users — always get it from the token.
- Always check resource ownership before allowing PUT, PATCH, or DELETE operations.
- Use 401 for missing/invalid token; use 403 for valid token but wrong permissions.
- Separate security layers: API endpoints enforce real security; frontend JS handles UX redirects.
- On account deletion, always clear the token client-side immediately.
- Always return 401 (not 404) when a user associated with a token doesn't exist — don't confirm user existence.
- Apply the `CurrentUser` dependency to all write endpoints (POST, PUT, PATCH, DELETE).
- Keep GET endpoints open unless the data is private — prefer auth-optional reads for public content.
