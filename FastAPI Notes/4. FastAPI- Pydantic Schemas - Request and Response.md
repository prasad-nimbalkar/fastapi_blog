## 1. What is Pydantic?

- A **data validation library** that uses Python type hints to enforce data types **at runtime**.
- In normal Python, type hints are just documentation — Pydantic actually **enforces** them.
- Gives detailed, structured error messages when data doesn't match the expected types.
- Comes **built into FastAPI** — no separate install needed.

> **Interview Tip:** Pydantic is what makes FastAPI's validation automatic. You define the shape of your data once using Python classes, and FastAPI + Pydantic handle validation, serialization, and documentation — all from the same definition.

---

## 2. Why Use Schemas Before a Database?

- **Schemas** define what data you accept from clients and what you return — the API contract.
- **Database models** define what you store — covered in the next step.
- Keeping these separate follows the **separation of concerns** principle.
- This is different from Flask, where validation was done manually with WTForms or `if` checks.

> **Interview Tip:** In FastAPI, Pydantic schemas and database models are intentionally different classes. Schemas handle API input/output; database models handle persistence. This separation makes the codebase cleaner and more maintainable.

---

## 3. Setting Up schemas.py

- Create a dedicated `schemas.py` file — keeps schemas separate from routes in `main.py`.

```python
from pydantic import BaseModel, ConfigDict, Field
```

| Import | Purpose |
|---|---|
| `BaseModel` | Base class all Pydantic models inherit from |
| `Field` | Adds constraints like `min_length`, `max_length` |
| `ConfigDict` | Pydantic v2 way to configure model behavior |

---

## 4. The Three Schema Classes

```
PostBase          ← shared fields (title, content, author)
   ├── PostCreate ← what the client sends when creating a post
   └── PostResponse ← what the API returns (includes id, date_posted)
```

### PostBase — shared fields

```python
class PostBase(BaseModel):
    title: str = Field(min_length=1, max_length=100)
    content: str = Field(min_length=1)
    author: str = Field(min_length=1, max_length=50)
```

### PostCreate — input schema

```python
class PostCreate(PostBase):
    pass  # inherits title, content, author from PostBase
```

- `pass` keeps it identical to `PostBase` for now.
- Having a separate class shows **intent** and gives flexibility later.
- Example: when authentication is added, `author` can be removed from `PostCreate` and taken from the logged-in user instead.

### PostResponse — output schema

```python
class PostResponse(PostBase):
    model_config = ConfigDict(from_attributes=True)

    id: int
    date_posted: str  # will become datetime when database is added
```

- Inherits `title`, `content`, `author` from `PostBase`.
- Adds `id` and `date_posted` — fields **generated by the system**, not provided by the client.

> **Important:** `PostCreate` is what goes **in**. `PostResponse` is what comes **out**. Never mix them up — they serve different purposes.

## 5. Field Validation with Constraints

```python
title: str = Field(min_length=1, max_length=100)
content: str = Field(min_length=1)
author: str = Field(min_length=1, max_length=50)
```

- Fields **without default values** are **required** — omitting them causes a 422 error.
- `min_length=1` — disallows empty strings.
- `max_length=100` — limits string length.
- These constraints appear automatically in `/docs` under the schema section.

> **Common Question:** *"How do you make a field required in Pydantic?"*
> Don't give it a default value. Fields with no default are required. Fields with `= None` or `= "default"` are optional.

---

## 6. `model_config` & `from_attributes`

```python
class PostResponse(PostBase):
    model_config = ConfigDict(from_attributes=True)
```

- **Pydantic v2** uses `ConfigDict` instead of the old inner `class Config`.
- `from_attributes=True` — allows Pydantic to read data from **objects with attributes** (dot notation), not just dictionaries (bracket notation).

| Data source | Access style | Works by default? |
|---|---|---|
| Dictionary | `post["title"]` | ✅ Yes |
| ORM object (database) | `post.title` | ❌ No — needs `from_attributes=True` |

> **Important:** Without `from_attributes=True`, Pydantic will fail when trying to serialize database model objects (SQLAlchemy rows). Always set this on response schemas.

> **Interview Tip:** In Pydantic v1 this was called `orm_mode = True` inside `class Config`. In Pydantic v2 it is `from_attributes=True` inside `ConfigDict`. You may see both in real codebases.

## 7. Using Schemas in main.py

```python
from schemas import PostCreate, PostResponse
```

- Only import what you use in `main.py`.
- `PostBase` stays in `schemas.py` — it's just a base class, not used directly in routes.

## 8. Response Models on GET Endpoints

```python
@app.get("/api/posts", response_model=list[PostResponse])
def get_posts():
    return posts

@app.get("/api/posts/{post_id}", response_model=PostResponse)
def get_post(post_id: int):
    ...
```

- `response_model` tells FastAPI what the response should look like.
- FastAPI **validates** the response against the schema before sending it.
- **Filters out** any extra fields not in the schema — prevents accidentally exposing sensitive data.
- **Shows the schema** in `/docs` — developers know exactly what to expect from the API.

> **Important:** `response_model` does two things: documents the API **and** acts as a safeguard by filtering/validating outgoing data.

## 9. Creating a POST Endpoint

```python
@app.post("/api/posts", response_model=PostResponse, status_code=status.HTTP_201_CREATED)
def create_post(post: PostCreate):
    new_id = max(p["id"] for p in posts) + 1  # temporary — database handles this later
    new_post = {
        "id": new_id,
        "title": post.title,
        "content": post.content,
        "author": post.author,
        "date_posted": "2026-01-01"  # hard-coded for now
    }
    posts.append(new_post)
    return new_post
```

- `@app.post()` — POST requests are used to **create** resources (REST convention).
- `post: PostCreate` — FastAPI sees this type hint, automatically parses the JSON request body, and validates it against `PostCreate`.
- `status_code=HTTP_201_CREATED` — REST best practice: return 201 when a resource is created, not 200.
- If validation fails → FastAPI returns 422 automatically, before the function runs.

> **Interview Tip:** The function parameter `post: PostCreate` is all FastAPI needs to parse and validate the entire request body. You don't write any parsing or validation code yourself.

## 10. How Automatic Validation Works

```
Client sends POST request with JSON body
         ↓
FastAPI reads PostCreate type hint on the parameter
         ↓
Pydantic validates the JSON against PostCreate schema
         ↓
  ┌──────────────────────────────────┐
  │ Valid? → function runs normally  │
  │ Invalid? → 422 returned          │
  │           (function never runs)  │
  └──────────────────────────────────┘
```

### Example validation errors

| Scenario | Error |
|---|---|
| Empty title `""` | `string should have at least 1 character` |
| Missing `author` field | `field required` |
| Title > 100 characters | `string should have at most 100 characters` |

- All errors returned as **structured JSON** with field name, error type, and message.
- **No `if` statements, no `try/except`** needed — Pydantic handles it all.

## 11. Why In-Memory Storage is Not Enough

```python
posts = [...]  # Python list in memory
```

- Data is lost every time the server restarts.
- Not shared across multiple server instances.
- Cannot handle concurrent writes safely.
- **Solution:** Use a real database (SQLAlchemy + SQLite/PostgreSQL — covered next).

> **Interview Tip:** In-memory lists are fine for prototyping and learning, but production APIs always persist data in a database. The Pydantic schemas you write now will still work the same way once the database is connected.

## 12. Common Interview Questions

**Q: What is Pydantic and why does FastAPI use it?**
> Pydantic is a data validation library using Python type hints. FastAPI uses it to automatically validate incoming request data, serialize outgoing responses, and generate API documentation — all from a single schema definition.

---

**Q: What is the difference between `PostCreate` and `PostResponse`?**
> `PostCreate` defines what the client sends when creating a resource (input). `PostResponse` defines what the API returns (output). They share common fields via `PostBase` but `PostResponse` adds server-generated fields like `id` and `date_posted`.

---

**Q: What does `response_model` do in FastAPI?**
> It validates and filters the data returned by a route against a Pydantic schema. It also generates documentation in `/docs` showing the exact response structure. Extra fields not in the schema are automatically removed.

---

**Q: What is `from_attributes=True` in Pydantic v2?**
> It allows Pydantic to read data from objects using dot notation (e.g. `post.title`) in addition to dictionaries. This is required when working with ORM database objects (like SQLAlchemy models) instead of plain dicts.

---

**Q: How do you make a field required vs optional in Pydantic?**
> A field with no default value is required. A field with `= None` or any default is optional.

```python
title: str               # required
description: str = None  # optional
```

---

**Q: What status code should a POST (create) endpoint return?**
> `201 Created` — not `200 OK`. This follows REST conventions and tells the client that a new resource was successfully created. In FastAPI: `status_code=status.HTTP_201_CREATED`.

---

**Q: What happens if a required field is missing in the request body?**
> Pydantic raises a `RequestValidationError` and FastAPI automatically returns a `422 Unprocessable Content` response with a detailed JSON error message. The route function never executes.

## 13. Common Mistakes & Pitfalls

> **Pitfall:** Using `PostResponse` as the input schema for a POST endpoint — it includes server-generated fields like `id` that the client should never send.

> **Pitfall:** Forgetting `from_attributes=True` on response schemas — Pydantic will fail when the database is added and ORM objects are returned instead of dicts.

> **Pitfall:** Using the old Pydantic v1 `orm_mode = True` syntax in Pydantic v2 — use `ConfigDict(from_attributes=True)` instead.

> **Pitfall:** Importing `PostBase` in `main.py` and using it directly as a response model — it's a base class meant only for inheritance, not direct use.

> **Pitfall:** Forgetting `status_code=HTTP_201_CREATED` on POST endpoints — returning 200 for resource creation violates REST conventions.

> **Pitfall:** Setting `min_length=0` thinking it makes a field optional — it still requires the field to be present; it just allows empty strings. Use `= None` to make a field truly optional.

---

## 14. Best Practices

- Always create a separate `schemas.py` file — don't define Pydantic models inside `main.py`.
- Use a base schema (`PostBase`) for shared fields and inherit from it — follows DRY principle.
- Always use `response_model` on every API endpoint — improves docs and prevents data leaks.
- Use `status.HTTP_201_CREATED` for POST endpoints that create resources.
- Use `Field(min_length=..., max_length=...)` to add meaningful constraints.
- Set `from_attributes=True` on all response schemas — prepares them for database integration.
- Keep `PostCreate` and `PostResponse` as separate classes even if they look identical now — they will diverge as the app grows (e.g. adding auth, computed fields).
- Use `list[PostResponse]` as the response model for endpoints returning multiple items.
