## 1. Authentication vs Authorization

### Core Concept Definition

- **Authentication:** *Who are you?* — Verifying identity (login, registration, token validation)
- **Authorization:** *What are you allowed to do?* — Verifying permissions (can this user edit this post?)

> **Why they're separated:** Authentication must be established before authorization can be checked. They're solved with different tools and logic — conflating them leads to security bugs.

### Interview-Relevant Details

| Concern | Question | Mechanism |
|---|---|---|
| Authentication | Is this user who they claim to be? | Password hashing, JWT, OAuth2 |
| Authorization | Is this user allowed to do this? | Route guards, ownership checks, roles |

### Common Interview Questions & Answers

❓ **"What is the difference between authentication and authorization?"**
> Authentication verifies identity — "I am user #42, here is my JWT token." Authorization verifies permissions — "User #42 is allowed to edit post #5 because they're the author." You need authentication to know *who* is making a request before you can determine *what* they're allowed to do.

❓ **"Can you have authorization without authentication?"**
> No — you can't enforce permissions for an unknown user. You can have public endpoints (no auth required) and protected endpoints (auth + optional authorization). But if a route requires ownership checks, authentication must happen first to establish identity.

### 🎯 Interview Tip
This distinction is asked in nearly every backend security interview. Always define both, give the "who vs what" summary, then walk through how they interact: *"JWT establishes identity (authentication); our ownership check `post.user_id == current_user.id` enforces access (authorization)."*

## 2. Password Hashing — Argon2 with passlib

### Core Concept Definition

**Password hashing** is a one-way transformation of a password into a fixed-length string. You can verify a password matches a hash, but you cannot reverse the hash back to the original password.

**Argon2** is the current gold standard for password hashing — the winner of the Password Hashing Competition (2015). More resistant to GPU/ASIC attacks than older algorithms like bcrypt or MD5.

### Setup and Usage

```python
# auth.py
from passlib.context import CryptContext

# Create hasher with Argon2 recommended settings
pwd_hasher = CryptContext.recommended()
# Or explicitly:
# pwd_hasher = CryptContext(schemes=["argon2"], deprecated="auto")

def hash_password(password: str) -> str:
    """Hash a plain-text password. Returns the hash string."""
    return pwd_hasher.hash(password)

def verify_password(plain_password: str, hashed_password: str) -> bool:
    """Returns True if the plain password matches the stored hash."""
    return pwd_hasher.verify(plain_password, hashed_password)
```

```python
# Usage in registration:
hashed = hash_password("mypassword123")
# → "$argon2id$v=19$m=65536,t=3,p=4$..."  (never the same twice)

# Usage in login:
is_valid = verify_password("mypassword123", stored_hash)
# → True

is_valid = verify_password("wrongpassword", stored_hash)
# → False
```

### Why Argon2 Over bcrypt/MD5/SHA

| Algorithm | Status | Concern |
|---|---|---|
| MD5/SHA-1/SHA-256 | **Never use for passwords** | Fast — trivially crackable with GPUs |
| bcrypt | OK but aging | Limited to 72 characters; less GPU resistant |
| **Argon2** | ✅ Current best practice | Memory-hard, configurable, GPU/ASIC resistant |

### The Salt — Why Same Password → Different Hash

```python
hash1 = hash_password("password123")
hash2 = hash_password("password123")

print(hash1 == hash2)  # False — different salt each time

# Argon2 generates a random salt on every hash() call
# The salt is embedded IN the hash string
# verify() extracts the salt from the stored hash automatically
```

> **Why salt matters:** Without unique salts, attackers can precompute a list of common password hashes ("rainbow tables") and look yours up instantly. Each unique salt means each hash must be cracked individually.

### Common Interview Questions & Answers

❓ **"How should passwords be stored in a database?"**
> Never store plain-text passwords. Hash them with a modern, slow hashing algorithm like Argon2 using a library like passlib. Store only the hash. On login, hash the submitted password and compare hashes — never compare against the original password.

❓ **"What is password salting and why is it important?"**
> A salt is a random value added to each password before hashing. It ensures identical passwords produce different hashes, defeating rainbow table attacks. Modern libraries like passlib handle salt generation and embedding automatically.

❓ **"Why use Argon2 instead of SHA-256 for passwords?"**
> SHA-256 is designed to be fast — ideal for data integrity, terrible for passwords. Argon2 is deliberately slow and memory-intensive, making brute-force and GPU attacks impractical. For passwords, you want hashing to be computationally expensive.

### 🎯 Interview Tip
Saying *"we use Argon2 because it's memory-hard — attackers can't just throw GPUs at it because high memory requirements limit parallelism"* shows advanced security awareness compared to just saying "we hash passwords."

## 3. Hashing vs Encryption — Why This Distinction Matters

### Core Concept Definition

| | Hashing | Encryption |
|---|---|---|
| **Reversible?** | ❌ No — one-way | ✅ Yes — with the key |
| **Use for passwords?** | ✅ Yes | ❌ No |
| **Use for sensitive data (SSN, CC)?** | ❌ No | ✅ Yes |
| **Examples** | Argon2, bcrypt, SHA-256 | AES, RSA |

> **For passwords:** You never need the original password — you just need to verify it. Hashing is correct because even if your DB is stolen, hashes can't be reversed.

> **For recoverable data:** If a user needs to see their own SSN or you need to send an email — you need encryption, not hashing. The data must be recoverable with a key.

### Common Interview Questions & Answers

❓ **"Should you encrypt or hash passwords?"**
> Hash — never encrypt. Encryption is reversible; if your encryption key is compromised, all passwords are exposed. Hashing is one-way — even with the hash and the algorithm, the password can't be recovered. You never need to recover the original password — you just need to verify it matches.

## 4. JSON Web Tokens (JWT) — Structure and Usage

### Core Concept Definition

A **JWT** (JSON Web Token) is a signed, compact, URL-safe token that proves a claim. Used as a stateless authentication mechanism — the server doesn't need to store sessions.

### JWT Structure

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwiZXhwIjoxNjE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
─────────────────────────────────────── ─────────────────────────────────────────── ──────────────────────────────────────────
HEADER (base64)                          PAYLOAD (base64)                            SIGNATURE (HMAC-SHA256)
{"alg": "HS256", "typ": "JWT"}           {"sub": "1", "exp": 1616239022}             Signed with SECRET_KEY
```

### Creating and Verifying Tokens

```python
# auth.py
import jwt
from datetime import datetime, timedelta, UTC
from config import settings

def create_access_token(data: dict, expires_delta: timedelta | None = None) -> str:
    to_encode = data.copy()
    expire = datetime.now(UTC) + (expires_delta or timedelta(minutes=30))
    to_encode.update({"exp": expire})

    return jwt.encode(
        to_encode,
        settings.secret_key.get_secret_value(),  # SecretStr requires explicit access
        algorithm=settings.algorithm
    )

def verify_access_token(token: str) -> str | None:
    """Returns user_id string if valid, None if invalid/expired."""
    try:
        payload = jwt.decode(
            token,
            settings.secret_key.get_secret_value(),
            algorithms=[settings.algorithm]
        )
        user_id: str = payload.get("sub")  # "sub" = subject (standard JWT claim)
        return user_id if user_id else None
    except jwt.PyJWTError:
        return None  # Invalid signature, expired, malformed — all return None
```

```python
# Usage
token = create_access_token({"sub": str(user.id)})
# → "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."

user_id = verify_access_token(token)
# → "42"  (or None if expired/invalid)
```

### Standard JWT Claims

| Claim | Full Name | Meaning |
|---|---|---|
| `sub` | Subject | Who the token is about (user ID) |
| `exp` | Expiration | Unix timestamp when token expires |
| `iat` | Issued At | When token was created |
| `iss` | Issuer | Who created the token |

### Why JWT for Stateless Auth

```
Traditional session-based:
  1. User logs in
  2. Server creates session, stores in DB/Redis
  3. Server returns session ID cookie
  4. Every request: server looks up session in storage ← DB call per request

JWT (stateless):
  1. User logs in
  2. Server creates signed JWT — NO storage needed
  3. Client stores JWT
  4. Every request: server verifies signature ← just cryptographic math, no DB
```

### Common Interview Questions & Answers

❓ **"What is a JWT and how does it work?"**
> A JWT is a signed token with three base64-encoded parts: header (algorithm), payload (claims like user ID and expiration), and signature (HMAC of header+payload with a secret key). The server can verify any token it receives just by re-computing the signature — no database lookup required. If the signature matches, the payload hasn't been tampered with.

❓ **"What is the `sub` field in a JWT?"**
> `sub` is the standard "subject" claim — it identifies who the token is about. In user auth, we store the user's ID here. It's a convention from the JWT spec (RFC 7519).

❓ **"How do you invalidate a JWT?"**
> Strictly speaking, you can't — the token is valid until its `exp` claim passes. Common mitigations: short expiration times (30 min), maintaining a server-side token blacklist (sacrifices statelessness), or rotating signing keys (invalidates all tokens). This is the main trade-off vs session-based auth.

❓ **"Can you read a JWT's payload without the secret key?"**
> Yes — the payload is base64-encoded, not encrypted. Anyone can decode and read it. The signature prevents tampering, but the payload is visible. Never put sensitive data (passwords, SSNs) in a JWT payload.

### 🎯 Interview Tip
The JWT invalidation question is a senior-level gotcha. Show you know the limitation: *"JWTs are stateless by design — this makes invalidation hard. We mitigate it with short expiration and requiring re-authentication for sensitive actions. For truly revocable tokens, a token blacklist in Redis is the common trade-off."*

## 5. Pydantic Settings — Secure Configuration Management

### Core Concept Definition

**`pydantic-settings`** loads and validates configuration from environment variables and `.env` files, with Pydantic's type validation and the `SecretStr` type to prevent accidental secret exposure.

### Setup

```python
# config.py
from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8"
    )

    secret_key: SecretStr           # Required — no default
    algorithm: str = "HS256"        # Optional — has default
    access_token_expire_minutes: int = 30  # Optional — has default

# Single instance — import this throughout the app
settings = Settings()  # type: ignore[call-arg]  # Values come from .env
```

```bash
# .env file (NEVER commit to git)
SECRET_KEY=a3f8d2e1b9c4a7f6e2d8b3c1a9f4e7d2b6c8a1f3e9d2b4c7a8f1e3d6b9c2a4f7
ALGORITHM=HS256  # optional — has default
ACCESS_TOKEN_EXPIRE_MINUTES=60  # override default
```

### SecretStr — Preventing Accidental Exposure

```python
settings = Settings()

# Accidental print — shows asterisks, not the real value
print(settings.secret_key)
# → **********

# Only explicit call reveals the value
print(settings.secret_key.get_secret_value())
# → "a3f8d2e1b9c4a7f6e2d8b3c1a9f4e7d2b6c8a1f3..."

# This protects against logs accidentally revealing secrets
logger.info(f"Config: {settings}")  # secret_key shows as **********
```

### Priority Order

```
1. System environment variables  (highest priority — for production)
2. .env file                     (for local development)
3. Field defaults in Settings    (fallback)

Required fields (no default) with no value → raises ValidationError at startup
```

### pydantic-settings vs python-dotenv

| Feature | pydantic-settings | python-dotenv |
|---|---|---|
| Type validation | ✅ Automatic | ❌ All strings |
| Missing required fields | ✅ Fails fast with clear error | ❌ Silent None |
| SecretStr protection | ✅ Built-in | ❌ None |
| Centralised config object | ✅ Settings class | ❌ Manual `os.getenv()` |

### Common Interview Questions & Answers

❓ **"How do you manage secrets in a FastAPI application?"**
> Use `pydantic-settings` with a `.env` file in development and system environment variables in production. The `.env` file is in `.gitignore` — never committed to version control. `SecretStr` fields prevent accidental exposure in logs. The `Settings` class validates all required config at startup, so the app fails loudly rather than silently missing a secret.

❓ **"What is `SecretStr` in Pydantic?"**
> A special string type that masks its value when printed or serialized. Calling `print(secret_str)` shows asterisks. You must explicitly call `.get_secret_value()` to access the actual string. This prevents accidental secret exposure in logs, error messages, or API responses.

## 6. OAuth2 Password Flow in FastAPI

### Core Concept Definition

**OAuth2 Password Flow** is an authentication pattern where the client sends username + password to a token endpoint and receives a bearer token. FastAPI has built-in support via `OAuth2PasswordBearer` and `OAuth2PasswordRequestForm`.

### The Flow

```
1. Client POST /api/users/token  { username: email, password: "..." }
2. Server validates credentials
3. Server returns { access_token: "eyJ...", token_type: "bearer" }
4. Client stores token
5. Subsequent requests: Authorization: Bearer eyJ...
6. Server extracts + verifies token on protected routes
```

### FastAPI Components

```python
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm

# Tells FastAPI where to get tokens — enables /docs "Authorize" button
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="api/users/token")
# tokenUrl must match the actual login endpoint path

# Login endpoint — OAuth2PasswordRequestForm parses form-encoded body
@router.post("/token", response_model=Token)
async def login(
    form_data: OAuth2PasswordRequestForm = Depends(),
    db: AsyncSession = Depends(get_db)
):
    # OAuth2PasswordRequestForm has:
    # form_data.username — we use this as email (OAuth2 quirk)
    # form_data.password
    # form_data.scope, form_data.grant_type (usually ignored)
    ...
```

### Content-Type Difference: Form vs JSON

```python
# Login endpoint expects FORM DATA (application/x-www-form-urlencoded)
# NOT JSON — this is an OAuth2 spec requirement

# OAuth2PasswordRequestForm automatically handles parsing form-encoded body
# Client must send: Content-Type: application/x-www-form-urlencoded

# JavaScript form submission:
const formData = new FormData(form)  # → sends as form-encoded
fetch("/api/users/token", { method: "POST", body: formData })
# ✅ Correct — FormData sends as application/x-www-form-urlencoded

fetch("/api/users/token", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ username, password })
})
# ❌ Wrong — OAuth2PasswordRequestForm expects form-encoded, not JSON
```

### Common Interview Questions & Answers

❓ **"What is OAuth2 Password Flow?"**
> It's a grant type where the client sends credentials directly to the token endpoint (not to a third-party authorization server). The server validates them and returns a bearer token. It's suitable for first-party clients (your own frontend) where you trust the client with credentials. For third-party OAuth (Google login, GitHub login), you'd use Authorization Code Flow.

❓ **"Why does `OAuth2PasswordRequestForm` use `username` even when we login with email?"**
> It's a quirk of the OAuth2 specification — the spec defines the field name as `username`. FastAPI uses the spec naming. In our implementation, we treat the `username` field as an email address. This is standard practice — the spec doesn't mandate that `username` must be a username; it's just the field name.

## 7. User Schema Design — Public vs Private Data

### Core Concept Definition

Different contexts should expose different amounts of user data. Returning email addresses in post responses is a privacy violation — viewers of a post don't need the author's email.

### Schema Hierarchy

```python
# schemas.py

class UserBase(BaseModel):
    username: str = Field(..., min_length=3, max_length=50)
    email: EmailStr

class UserCreate(UserBase):
    password: str = Field(..., min_length=8)  # Plain text — hashed before storing

class UserPublic(BaseModel):
    """For embedding in post responses — no email, minimal data."""
    id: int
    username: str
    image_file: str | None = None
    image_path: str | None = None

    class Config:
        from_attributes = True

class UserPrivate(UserPublic):
    """For the user viewing their own data — includes email."""
    email: EmailStr  # Only visible to the authenticated user

class Token(BaseModel):
    """Login response."""
    access_token: str
    token_type: str  # Always "bearer"

class PostResponse(BaseModel):
    id: int
    title: str
    content: str
    author: UserPublic  # ← UserPublic, NOT UserPrivate — no email in posts
```

### When to Use Which

| Endpoint | Schema | Why |
|---|---|---|
| `GET /api/posts` | `author: UserPublic` | Public — no email needed |
| `POST /api/users` (register) | Returns `UserPrivate` | User just created account — show their own data |
| `GET /api/users/me` | Returns `UserPrivate` | User viewing own profile |
| `GET /api/users/{id}` | Returns `UserPublic` | Public profile page |
| `PATCH /api/users/{id}` | Returns `UserPrivate` | User updating own data |

### Common Interview Questions & Answers

❓ **"How do you prevent API responses from leaking sensitive user data?"**
> Design separate response schemas for public and private contexts. A `UserPublic` schema for embedding in posts or public profiles contains only non-sensitive fields (username, image). A `UserPrivate` schema for the authenticated user inherits from `UserPublic` and adds sensitive fields like email. Use the appropriate schema per endpoint.

## 8. Registration Endpoint — Secure User Creation

### Core Concept Definition

User registration must: hash the password before storing, enforce uniqueness constraints (case-insensitively), and never return the password hash in the response.

### Complete Secure Registration

```python
@router.post("", response_model=UserPrivate, status_code=201)
async def create_user(user_data: UserCreate, db: AsyncSession = Depends(get_db)):
    # Check username uniqueness — case-insensitive
    existing = await db.execute(
        select(User).where(func.lower(User.username) == user_data.username.lower())
    )
    if existing.scalar_one_or_none():
        raise HTTPException(status_code=400, detail="Username already taken")

    # Check email uniqueness — case-insensitive
    existing = await db.execute(
        select(User).where(func.lower(User.email) == user_data.email.lower())
    )
    if existing.scalar_one_or_none():
        raise HTTPException(status_code=400, detail="Email already registered")

    # Create user:
    # - Preserve original username casing for display (Corey not corey)
    # - Normalize email to lowercase (emails are case-insensitive)
    # - HASH the password — NEVER store plain text
    new_user = User(
        username=user_data.username,          # Keep original casing
        email=user_data.email.lower(),        # Normalize email
        password_hash=hash_password(user_data.password)  # Hash, never plain
    )
    db.add(new_user)
    await db.commit()
    await db.refresh(new_user)
    return new_user
```

### Common Interview Questions & Answers

❓ **"What security checks should a registration endpoint perform?"**
> Hash the password before storing — never store plain text. Check uniqueness constraints case-insensitively (username "Corey" and "corey" should conflict). Normalize emails to lowercase. Never return the password hash in the response. Validate password strength (minimum length, complexity) at the schema level.

## 9. Login Endpoint — Token Generation

### Core Concept Definition

The login endpoint verifies credentials and returns a JWT. **Critical security rule:** return the same error for wrong email AND wrong password — never reveal which one failed.

### Implementation

```python
from datetime import timedelta
from fastapi.security import OAuth2PasswordRequestForm

@router.post("/token", response_model=Token)
async def login(
    form_data: OAuth2PasswordRequestForm = Depends(),
    db: AsyncSession = Depends(get_db)
):
    # Look up user by email (case-insensitive)
    # form_data.username = the email (OAuth2 spec naming quirk)
    result = await db.execute(
        select(User).where(func.lower(User.email) == form_data.username.lower())
    )
    user = result.scalar_one_or_none()

    # SECURITY: same error for wrong email OR wrong password
    # Never reveal which one failed — prevents user enumeration attacks
    if not user or not verify_password(form_data.password, user.password_hash):
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Incorrect email or password",
            headers={"WWW-Authenticate": "Bearer"}  # OAuth2 spec requirement
        )

    # Create JWT with user ID as the subject
    access_token = create_access_token(
        data={"sub": str(user.id)},
        expires_delta=timedelta(minutes=settings.access_token_expire_minutes)
    )

    return Token(access_token=access_token, token_type="bearer")
```

### Why the Same Error for Wrong Email/Password

```
❌ WRONG — reveals which field failed:
"Email not found"         → attacker knows which emails exist in your system
"Incorrect password"      → attacker knows the email is valid, focus on password

✅ CORRECT — same error for both:
"Incorrect email or password"  → attacker learns nothing
```

> This prevents **user enumeration attacks** — systematically discovering which email addresses have accounts.

### Common Interview Questions & Answers

❓ **"Why should login return the same error whether the email or password is wrong?"**
> To prevent user enumeration attacks. If "email not found" is a distinct error, attackers can systematically test email addresses to discover which ones have accounts in your system — then target those for phishing or brute-force attacks. A generic "incorrect credentials" error leaks no information.

❓ **"What should the `WWW-Authenticate` header contain for a 401 response?"**
> `Bearer` for JWT/OAuth2 APIs — it tells the client what authentication scheme to use. It's technically required by the OAuth2 spec when returning a 401, though many implementations omit it.

## 10. The `/me` Endpoint — Current User Pattern

### Core Concept Definition

The `/me` endpoint validates the current user's token and returns their full user data. It serves as both token validation and user data retrieval for the frontend.

### Why `/me` Instead of Decoding Token Client-Side

```
Decoding JWT in JavaScript:
  ✅ No network request
  ❌ Doesn't validate the token is still accepted by the server
  ❌ Doesn't catch server-side invalidation (key rotation, forced logout)

Calling /me endpoint:
  ✅ Server validates the token cryptographically
  ✅ Catches edge cases (DB user deleted after token issued)
  ✅ Returns fresh user data (not stale claims in old token)
  ❌ Network request on every page load
```

### Implementation

```python
@router.get("/me", response_model=UserPrivate)
async def get_current_user_endpoint(
    token: str = Depends(oauth2_scheme),  # Extracts Bearer token from header
    db: AsyncSession = Depends(get_db)
):
    # Verify token and extract user_id
    user_id_str = verify_access_token(token)
    if user_id_str is None:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Invalid or expired token",
            headers={"WWW-Authenticate": "Bearer"}
        )

    # Defensive conversion — token payload should be int, but validate
    try:
        user_id = int(user_id_str)
    except (ValueError, TypeError):
        raise HTTPException(status_code=401, detail="Invalid token payload")

    # Fetch user from DB
    result = await db.execute(select(User).where(User.id == user_id))
    user = result.scalar_one_or_none()
    if not user:
        raise HTTPException(status_code=401, detail="User not found")

    return user
```

### Route Ordering — Specific Before Parameterised

```python
# CRITICAL: /me must be defined BEFORE /{user_id}
# FastAPI matches routes in order of definition

@router.get("/me", ...)           # ← Define first — matches literal "me"
async def get_current_user(): ...

@router.get("/{user_id}", ...)    # ← Define after — would match "me" as a string otherwise
async def get_user(): ...
```

## 11. Case-Insensitive Uniqueness Checks

### Core Concept Definition

Database `UNIQUE` constraints are often case-sensitive by default. Without case-insensitive checks, "Corey" and "corey" could both register, creating confusion. All uniqueness checks for usernames and emails should be case-insensitive.

### Implementation

```python
from sqlalchemy import func

# Case-insensitive username check using func.lower()
result = await db.execute(
    select(User).where(
        func.lower(User.username) == user_data.username.lower()
    )
)

# Case-insensitive email check
result = await db.execute(
    select(User).where(
        func.lower(User.email) == user_data.email.lower()
    )
)
```

### Storage Decisions

```python
# Username: preserve original casing for display
# "Corey" displays as "Corey", not "corey"
new_user.username = user_data.username          # Keep as-is

# Email: normalise to lowercase
# Emails are case-insensitive by RFC spec — normalise for consistency
new_user.email = user_data.email.lower()        # Always lowercase
```

### Database Index Consideration

```python
# In production: add a functional index on lower(username) for performance
# Without index, every uniqueness check does a full table scan

# SQLAlchemy 2.x:
from sqlalchemy import Index, func

class User(Base):
    username = mapped_column(String(50))
    email = mapped_column(String(200))

    __table_args__ = (
        Index("ix_users_username_lower", func.lower(username), unique=True),
        Index("ix_users_email_lower", func.lower(email), unique=True),
    )
```

## 12. Frontend Token Storage — Local Storage vs HttpOnly Cookies

### Core Concept Definition

After login, the client must store the JWT somewhere for subsequent requests. The two main options have different security profiles.

### Comparison

| Approach | Access by JS | XSS Risk | CSRF Risk | Best For |
|---|---|---|---|---|
| **Local Storage** | ✅ Yes | ❌ Vulnerable | ✅ Safe | API-first apps, mobile clients |
| **HttpOnly Cookie** | ❌ No | ✅ Safe | ❌ Vulnerable | Browser-only apps |

### Local Storage Pattern (Used in This Tutorial)

```javascript
// On successful login
const data = await response.json();
localStorage.setItem("access_token", data.access_token);

// On subsequent API calls
const token = localStorage.getItem("access_token");
fetch("/api/posts", {
    headers: { "Authorization": `Bearer ${token}` }
});

// On logout
localStorage.removeItem("access_token");
```

### Security Considerations

```
Local Storage XSS risk:
  - If malicious JS runs on your page (via XSS), it can read localStorage
  - Mitigation: sanitize ALL user input, short token expiration

HttpOnly Cookie XSS protection:
  - JS cannot access HttpOnly cookies — even if XSS runs, token is safe
  - CSRF vulnerability: malicious sites can trigger cookie-bearing requests
  - Mitigation: CSRF tokens, SameSite cookie attribute

For an API-first app (web + mobile + third-party):
  → Local Storage / Authorization header — works for all clients
For a browser-only app:
  → HttpOnly cookies — better XSS protection
```

### The Authorization Header Format

```javascript
// Standard Bearer token format — required for OAuth2
headers: {
    "Authorization": `Bearer ${token}`
}
// "Bearer " prefix is mandatory — don't forget the space
```

### Common Interview Questions & Answers

❓ **"Where should you store JWT tokens in a browser and why?"**
> The two options are local storage and HttpOnly cookies. Local storage is accessible via JavaScript — convenient but vulnerable to XSS attacks. HttpOnly cookies are inaccessible to JavaScript — more XSS-safe but vulnerable to CSRF. For API-first applications that need to work across web, mobile, and other clients, local storage with short token expiration is pragmatic. For browser-only apps, HttpOnly cookies provide better security.

## 13. Security Best Practices Checklist

### Never Do

```python
# ❌ NEVER store plain text passwords
user.password = "mypassword"  # Criminal offence in some jurisdictions

# ❌ NEVER return password hashes in API responses
class UserResponse(BaseModel):
    password_hash: str  # Exposes the hash — still a security risk

# ❌ NEVER put secrets in code
SECRET_KEY = "hardcoded_secret"  # Committed to git = compromised

# ❌ NEVER reveal which credential was wrong
"Email not found"  # User enumeration vulnerability

# ❌ NEVER put sensitive data in JWT payload
{"sub": "1", "password_hash": "..."}  # JWT is base64 — not encrypted!

# ❌ NEVER commit .env to git
# Add .env to .gitignore immediately
```

### Always Do

```python
# ✅ Hash passwords with Argon2 before storing
user.password_hash = hash_password(plain_password)

# ✅ Use SecretStr for secrets in config
secret_key: SecretStr

# ✅ Validate tokens server-side — don't trust client-decoded claims
user_id = verify_access_token(token)  # Server verifies signature

# ✅ Same error for invalid email OR password
"Incorrect email or password"  # No enumeration

# ✅ Set reasonable token expiration
timedelta(minutes=30)  # Not timedelta(days=365)

# ✅ Use HTTPS in production — tokens in transit must be encrypted

# ✅ Case-insensitive uniqueness for usernames and emails
func.lower(User.email) == email.lower()

# ✅ Normalize emails to lowercase on storage
user.email = email.lower()
```

## Quick Revision Cheat Sheet

```
Authentication = WHO are you? (login, JWT)
Authorization  = WHAT can you do? (ownership checks, roles)

Password storage:
  hash()   → Argon2 one-way (use for passwords)
  encrypt  → reversible (use for recoverable data, NOT passwords)
  salt     → random per-password, prevents rainbow tables
  passlib  → handles hash(), verify(), salt automatically

JWT structure: header.payload.signature (all base64)
  sub  → user ID (subject)
  exp  → expiration timestamp
  Payload is readable without key — never put secrets there
  Signature prevents tampering — requires secret key to verify

create_access_token({"sub": str(user.id)})
verify_access_token(token) → user_id_str | None

OAuth2 flow:
  POST /token  form-encoded body (NOT JSON)
  → { access_token, token_type: "bearer" }
  → Subsequent requests: Authorization: Bearer <token>

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="api/users/token")
  → Extracts token from Authorization header
  → Enables /docs Authorize button

SecretStr.get_secret_value()  → only way to access actual string
  print(secret)  → **********  (safe in logs)

User schemas:
  UserPublic  → id, username, image (for embedding in posts)
  UserPrivate → UserPublic + email (for user's own data)
  Token       → access_token, token_type

Security rules:
  Same error for wrong email AND wrong password (no enumeration)
  Normalize email to lowercase, preserve username casing
  func.lower(User.email) == email.lower()  (case-insensitive DB check)

Route ordering: /me before /{user_id} (specific before parameterised)

Token storage:
  localStorage  → XSS risk, works all clients, bearer header
  HttpOnly cookie → XSS safe, CSRF risk, browser only
  API-first → localStorage; browser-only → HttpOnly cookie
```
