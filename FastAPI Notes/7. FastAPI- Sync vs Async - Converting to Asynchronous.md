## 1. Synchronous vs Asynchronous Execution

### Core Concept Definition

**Synchronous (sync):** Code executes line by line. Each operation must complete before the next one starts. Like a Subway sandwich shop — the worker makes your entire sandwich before serving the next customer.

**Asynchronous (async):** Code can *pause* during waiting operations and handle other tasks in the meantime. Like McDonald's — your order is placed, and while the kitchen prepares it, the cashier takes the next order.

> **Why it exists:** Servers handle many concurrent requests. If every request blocks while waiting for a DB response, the server wastes time doing nothing. Async lets other requests be processed during those waits.

### Interview-Relevant Details

- **Key vocabulary:** event loop, coroutine, `await`, `async def`, concurrency, IO-bound, non-blocking
- **asyncio** is Python's standard library for async programming; FastAPI is built on top of it via **Starlette**
- **Concurrency ≠ Parallelism:** Async achieves concurrency (interleaving tasks) on a single thread, not true parallel execution

### Common Interview Questions & Answers

❓ **"What is the difference between sync and async in Python?"**
> Sync executes tasks sequentially; async allows a task to yield control while waiting (e.g., for a DB query), so the event loop can run other coroutines during that time.

❓ **"Is async always faster?"**
> No. For a single, fast request with no concurrent load, async adds slight overhead. The real benefit appears under **high concurrency** — many simultaneous requests.

❓ **"What is a coroutine?"**
> A function defined with `async def` that can be paused with `await`. It returns a coroutine object that must be awaited or scheduled on the event loop.

### Practical Code Example

```python
import asyncio

# Synchronous — blocks for each task
def fetch_data_sync():
    time.sleep(2)  # Blocks everything for 2 seconds
    return "data"

# Asynchronous — yields control during the wait
async def fetch_data_async():
    await asyncio.sleep(2)  # Pauses THIS coroutine, event loop runs others
    return "data"
```

### 🎯 Interview Tip
Mention the **McDonald's vs Subway** analogy — it's memorable and shows conceptual clarity. Then follow up with the technical explanation. Interviewers appreciate both clarity of thought and depth.

## 2. FastAPI's Handling of Sync vs Async Routes

### Core Concept Definition

FastAPI treats `def` and `async def` routes differently — but **both are safe to use**:

| Route Type | How FastAPI Handles It |
|---|---|
| `def` (sync) | Runs in a **thread pool** (via `run_in_executor`) — doesn't block the event loop |
| `async def` | Runs directly on the **event loop** — more efficient, but you MUST await IO |

### Interview-Relevant Details

- FastAPI uses **Starlette** under the hood, which manages the event loop
- Sync routes in FastAPI are **not** as slow as raw sync code — they're offloaded to threads automatically
- **Thread pool** = a group of pre-created threads ready to handle work (avoids the cost of spawning new threads per request)

### Common Interview Questions & Answers

❓ **"Does using `def` instead of `async def` in FastAPI block other requests?"**
> No. FastAPI automatically runs `def` routes in a thread pool executor, so they don't block the event loop. Other requests continue to be handled concurrently.

❓ **"What happens if you do blocking IO inside an `async def` route?"**
> You block the entire event loop. All other requests stall until that operation finishes. This is **worse** than using a plain `def` route, because at least `def` routes get their own thread.

```python
# ❌ DANGEROUS — blocking IO inside async route
async def get_user():
    result = requests.get("https://api.example.com")  # requests is SYNCHRONOUS
    return result.json()  # Blocks the entire event loop!

# ✅ CORRECT — use async-compatible library
async def get_user():
    async with httpx.AsyncClient() as client:
        result = await client.get("https://api.example.com")
    return result.json()
```

### 🎯 Interview Tip
This is a **very common** interview gotcha. Saying "you must use `async def` for performance" is incomplete. The correct answer is: *"It depends on whether your route does IO, and whether your libraries support async."*

## 3. IO-bound vs CPU-bound Operations

### Core Concept Definition

- **IO-bound:** Time is spent *waiting* for external resources — database, network, disk. The CPU is idle during this time. → **Async helps here.**
- **CPU-bound:** Time is spent *computing* — image processing, ML inference, data crunching. The CPU is fully busy. → **Async does NOT help here.**

### Interview-Relevant Details

| Category | Examples | Solution |
|---|---|---|
| IO-bound | DB queries, API calls, file reads | `async def` + `await` |
| CPU-bound | Image resize, encryption, data crunching | `multiprocessing`, `ProcessPoolExecutor`, background tasks |

### Common Interview Questions & Answers

❓ **"When would async NOT improve performance?"**
> For CPU-bound tasks like image processing or heavy calculations. Async only frees the event loop during *waiting*, not during *computing*. For CPU work, use `multiprocessing` or worker processes.

❓ **"How would you handle a CPU-heavy task in FastAPI?"**
> Use FastAPI's `BackgroundTasks`, or offload to a task queue like **Celery** with Redis/RabbitMQ. For async-friendly CPU work, use `asyncio.run_in_executor` with a `ProcessPoolExecutor`.

### 🎯 Interview Tip
Showing awareness of CPU-bound vs IO-bound is a strong signal to interviewers. Many candidates only know "async = fast." Knowing *when* it helps (and when it doesn't) demonstrates real understanding.

## 4. Async SQLAlchemy Setup

### Core Concept Definition

Standard SQLAlchemy uses synchronous drivers. For async FastAPI apps, you need:
1. An **async database driver** (e.g., `aiosqlite` for SQLite, `asyncpg` for PostgreSQL)
2. SQLAlchemy's **async engine and session** from `sqlalchemy.ext.asyncio`

### Interview-Relevant Details

- **`create_async_engine`** — async version of `create_engine`; uses an async driver under the hood
- **`async_sessionmaker`** — async version of `sessionmaker`; produces `AsyncSession` objects
- **`expire_on_commit=False`** — critical for async; prevents SQLAlchemy from lazy-loading expired attributes after a commit (lazy loading doesn't work in async)
- **Driver string:** Add `+aiosqlite` or `+asyncpg` to the database URL

### Practical Code Example

```python
# database.py — Async Setup

from sqlalchemy.ext.asyncio import (
    AsyncSession,
    async_sessionmaker,
    create_async_engine,
)
from sqlalchemy.orm import declarative_base

# SQLite: sqlite+aiosqlite    PostgreSQL: postgresql+asyncpg
DATABASE_URL = "sqlite+aiosqlite:///./app.db"

# Async engine
engine = create_async_engine(DATABASE_URL)

# Async session factory
# expire_on_commit=False prevents lazy-load errors after commit
AsyncSessionLocal = async_sessionmaker(
    bind=engine,
    class_=AsyncSession,
    expire_on_commit=False,
)

Base = declarative_base()

# Async dependency for routes
async def get_db():
    async with AsyncSessionLocal() as session:
        yield session
```

### Before vs After

```python
# BEFORE — Synchronous
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, Session

engine = create_engine("sqlite:///./app.db")
SessionLocal = sessionmaker(bind=engine)

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

# AFTER — Asynchronous
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker, AsyncSession

engine = create_async_engine("sqlite+aiosqlite:///./app.db")
AsyncSessionLocal = async_sessionmaker(bind=engine, class_=AsyncSession, expire_on_commit=False)

async def get_db():
    async with AsyncSessionLocal() as session:
        yield session
```

### Common Interview Questions & Answers

❓ **"Why do you need `expire_on_commit=False` in async SQLAlchemy?"**
> After a commit, SQLAlchemy normally marks objects as "expired" and refreshes them lazily on next access. In async, lazy loading is not supported — it would require a sync query. Setting `expire_on_commit=False` keeps attribute values in memory and avoids the lazy-load attempt.

❓ **"What is the async driver for PostgreSQL in SQLAlchemy?"**
> `asyncpg`. The connection string becomes `postgresql+asyncpg://user:password@host/db`.

### 🎯 Interview Tip
For data engineering roles at BFSI companies (like your current work), interviewers often ask about **PostgreSQL + asyncpg** specifically. Mention that the pattern is identical — just swap the driver and connection string.

## 5. Lifespan Events (Startup & Shutdown)

### Core Concept Definition

**Lifespan** is FastAPI's modern way to run code at application startup and shutdown. Used for:
- Creating database tables on startup
- Initializing connection pools
- Cleaning up resources on shutdown

> **Why it exists:** Replaces the older (now deprecated) `@app.on_event("startup")` and `@app.on_event("shutdown")` decorators. Provides a cleaner, context-manager-based approach.

### Interview-Relevant Details

- Uses Python's `@asynccontextmanager` decorator
- Code **before** `yield` = startup logic
- Code **after** `yield` = shutdown logic
- The `yield` itself = while the app is running
- Must be passed to `FastAPI(lifespan=lifespan)`

### Practical Code Example

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    # ── STARTUP ──────────────────────────────────
    async with engine.begin() as conn:
        # run_sync lets us call synchronous SQLAlchemy
        # methods inside an async context
        await conn.run_sync(Base.metadata.create_all)
    print("App started, tables created")

    yield  # ← App runs here

    # ── SHUTDOWN ─────────────────────────────────
    await engine.dispose()
    print("App shutting down, engine disposed")

app = FastAPI(lifespan=lifespan)
```

### Common Interview Questions & Answers

❓ **"How do you run startup logic in FastAPI?"**
> Use the `lifespan` context manager with `@asynccontextmanager`. Code before `yield` runs at startup; code after runs at shutdown. Pass it to `FastAPI(lifespan=lifespan)`.

❓ **"What replaced `@app.on_event` in FastAPI?"**
> The `lifespan` context manager pattern. `on_event` is still functional but deprecated.

❓ **"Why use `run_sync` inside `engine.begin()`?"**
> SQLAlchemy's `metadata.create_all()` is a synchronous method. Inside an async context, we can't call it directly. `run_sync` safely executes it in the async context by running it in a thread executor.

### 🎯 Interview Tip
Knowing that `@app.on_event` is deprecated and lifespan is the modern approach immediately signals that you keep up with FastAPI best practices — a strong positive signal in interviews.

## 6. Eager Loading vs Lazy Loading in Async SQLAlchemy

### Core Concept Definition

**Lazy Loading (sync only):** SQLAlchemy automatically fetches related objects when you access a relationship attribute. Works silently in synchronous code.

```python
post = db.query(Post).first()
print(post.author.username)  # SQLAlchemy silently runs a 2nd query here
```

**Eager Loading (required for async):** You explicitly tell SQLAlchemy to load related objects in the *same* query, upfront.

> **Why lazy loading breaks in async:** Lazy loading would need to fire a synchronous database query mid-coroutine. That's not allowed in async SQLAlchemy — it raises a `MissingGreenlet` error.

### Interview-Relevant Details

- **`selectinload`** — loads relationships using a separate `SELECT ... WHERE IN (...)` query, but does it eagerly at query time
- **`joinedload`** — uses a SQL JOIN to load relationships in the same query (better for one-to-one or many-to-one)
- **`MissingGreenlet` error** — the specific error you get when you accidentally trigger lazy loading in async SQLAlchemy
- **`db.refresh(obj, attribute_names=["author"])`** — eager-loads specific relationships on an already-fetched object (useful post-commit)

### Practical Code Example

```python
from sqlalchemy import select
from sqlalchemy.orm import selectinload

# ❌ WRONG in async — triggers lazy loading
async def get_posts(db: AsyncSession):
    result = await db.execute(select(Post))
    posts = result.scalars().all()
    # Accessing post.author here raises MissingGreenlet!
    return posts

# ✅ CORRECT — eager load the relationship upfront
async def get_posts(db: AsyncSession):
    result = await db.execute(
        select(Post).options(selectinload(Post.author))  # Load author in same query
    )
    posts = result.scalars().all()
    return posts  # post.author is already loaded ✓

# ✅ CORRECT — eager load after commit using refresh
async def create_post(post_data, db: AsyncSession):
    new_post = Post(**post_data)
    db.add(new_post)          # No await needed — in-memory operation
    await db.commit()         # Await needed — hits the database
    await db.refresh(new_post, attribute_names=["author"])  # Load author
    return new_post
```

### Common Interview Questions & Answers

❓ **"What is the difference between lazy and eager loading in SQLAlchemy?"**
> Lazy loading fetches related objects on demand when you access the attribute — happens automatically. Eager loading fetches related objects upfront as part of the original query, using `selectinload` or `joinedload`.

❓ **"Why doesn't lazy loading work in async SQLAlchemy?"**
> Lazy loading requires a synchronous blocking database call mid-execution. In async mode, there's no active event loop thread for SQLAlchemy to block, so it raises a `MissingGreenlet` error. You must use eager loading instead.

❓ **"What is `selectinload` vs `joinedload`?"**
> `selectinload` issues a second SELECT query with a WHERE IN clause — better for one-to-many (e.g., a post's many comments). `joinedload` uses a SQL JOIN — better for many-to-one or one-to-one (e.g., a post's single author). Both achieve eager loading.

❓ **"When would you use `db.refresh` with `attribute_names`?"**
> After creating or updating an object and committing, when you need a relationship loaded on the returned object without re-querying. It's more efficient than running a whole new SELECT with `selectinload`.

### 🎯 Interview Tip
The `MissingGreenlet` error is a **classic async SQLAlchemy gotcha** that comes up in senior-level interviews. Knowing its cause and fix immediately demonstrates real hands-on async experience.

## 7. Async Route Patterns & Awaitable Operations

### Core Concept Definition

In async FastAPI routes, you must `await` any operation that involves IO. The rule: **if it touches the database, network, or disk — `await` it.**

### What Needs `await` vs What Doesn't

| Operation | Needs `await`? | Why |
|---|---|---|
| `db.execute(...)` | ✅ Yes | Hits the database |
| `db.commit()` | ✅ Yes | Writes to the database |
| `db.refresh(obj)` | ✅ Yes | Re-reads from the database |
| `db.delete(obj)` | ✅ Yes | Interacts with the session async state |
| `db.add(obj)` | ❌ No | In-memory only — adds to pending list |
| `result.scalars().all()` | ❌ No | In-memory processing of already-fetched result |

### Practical Code Example

```python
from fastapi import APIRouter, Depends
from sqlalchemy.ext.asyncio import AsyncSession
from sqlalchemy import select
from sqlalchemy.orm import selectinload

router = APIRouter()

@router.get("/posts")
async def get_posts(db: AsyncSession = Depends(get_db)):
    result = await db.execute(           # ← await: hits DB
        select(Post).options(selectinload(Post.author))
    )
    return result.scalars().all()

@router.post("/posts")
async def create_post(data: PostCreate, db: AsyncSession = Depends(get_db)):
    post = Post(**data.dict())
    db.add(post)                          # ← NO await: in-memory
    await db.commit()                     # ← await: writes to DB
    await db.refresh(post, attribute_names=["author"])  # ← await: reads from DB
    return post

@router.delete("/posts/{post_id}")
async def delete_post(post_id: int, db: AsyncSession = Depends(get_db)):
    result = await db.execute(select(Post).where(Post.id == post_id))
    post = result.scalar_one_or_none()
    if post:
        await db.delete(post)             # ← await: async session interaction
        await db.commit()                 # ← await: writes to DB
    return {"deleted": post_id}
```

### 🎯 Interview Tip
A subtle but impressive detail: explaining **why `db.add()` doesn't need `await`** (it's purely in-memory, no IO) while `db.delete()` does (it interacts with the async session state) shows genuine understanding, not just pattern copying.

## 8. Async Exception Handlers

### Core Concept Definition

FastAPI allows you to define custom exception handlers. In async apps, these should also be async and use FastAPI's built-in default handlers for standard exceptions (`HTTPException`, `RequestValidationError`).

### Interview-Relevant Details

- FastAPI provides default async handlers: `http_exception_handler`, `request_validation_exception_handler`
- Import from `fastapi.exception_handlers`
- You can override for custom behavior (e.g., different format for API vs template routes) while still delegating to the default handler for the actual response

### Practical Code Example

```python
from fastapi import FastAPI, Request
from fastapi.exception_handlers import (
    http_exception_handler,
    request_validation_exception_handler,
)
from fastapi.exceptions import RequestValidationError
from starlette.exceptions import HTTPException

app = FastAPI()

@app.exception_handler(HTTPException)
async def custom_http_exception_handler(request: Request, exc: HTTPException):
    if request.url.path.startswith("/api"):
        # API routes: delegate to FastAPI's default JSON handler
        return await http_exception_handler(request, exc)
    # Template routes: return HTML error page
    return templates.TemplateResponse("error.html", {"detail": exc.detail}, status_code=exc.status_code)

@app.exception_handler(RequestValidationError)
async def custom_validation_handler(request: Request, exc: RequestValidationError):
    return await request_validation_exception_handler(request, exc)
```

### Common Interview Questions & Answers

❓ **"How do you handle errors differently for API vs HTML routes in FastAPI?"**
> Use a custom exception handler that checks `request.url.path`. For API routes (starting with `/api`), return JSON. For template routes, render an HTML error page. In async apps, delegate to FastAPI's built-in async handlers.

## 9. When to Use Async vs Sync

### Decision Framework

```
Does your route do IO? (DB, network, file)
    ├── YES → Does your library support async? (asyncpg, httpx, aiofiles)
    │           ├── YES → Use async def + await
    │           └── NO  → Use def (FastAPI threads it safely)
    └── NO  → Does it do heavy CPU work?
                ├── YES → Use def + background tasks / Celery
                └── NO  → Either works; prefer simplicity
```

### Summary Table

| Scenario | Recommendation |
|---|---|
| Database queries (high concurrency) | `async def` |
| External API calls | `async def` + `httpx` |
| File operations | `async def` + `aiofiles` |
| Simple fast routes | Either — `def` is fine |
| Heavy calculations | `def` + offload to worker |
| Using sync-only libraries | `def` (FastAPI threads it) |
| Mixed routes in same app | ✅ Totally fine — mix as needed |

### Common Interview Questions & Answers

❓ **"Do all routes in a FastAPI app need to be async?"**
> No. FastAPI supports mixing sync and async routes in the same app. Choose based on what each route actually does. Sync routes are automatically run in a thread pool, so they don't block other requests.

❓ **"What sync libraries should you avoid in async routes?"**
> The `requests` library (use `httpx` instead), synchronous SQLAlchemy sessions (use `AsyncSession`), blocking file operations (use `aiofiles`), and `time.sleep` (use `await asyncio.sleep`).

### 🎯 Interview Tip
Saying "I use async where IO is involved and sync where it isn't — and I always check if my libraries support async" is a mature, production-grade answer. Avoid saying "I always use async for everything."

## 10. Common Mistakes & Best Practices

### ❌ Common Mistakes

| Mistake | Why It's Wrong | Fix |
|---|---|---|
| Using `requests` in `async def` | Blocks the event loop | Use `httpx.AsyncClient` |
| Not awaiting `db.commit()` | Changes aren't persisted; silent bug | Always `await db.commit()` |
| Accessing relationships without eager load | `MissingGreenlet` error | Use `selectinload` or `joinedload` |
| Using `time.sleep` in async code | Blocks the event loop | Use `await asyncio.sleep()` |
| Setting `expire_on_commit=True` (default) with async | Lazy reload errors after commit | Set `expire_on_commit=False` |
| Calling `create_all()` directly with async engine | Sync method, async context conflict | Use `engine.begin()` + `run_sync` in lifespan |
| Forgetting `greenlet` installation | Runtime error with async SQLAlchemy | `pip install greenlet` |

### ✅ Best Practices

- **Install `greenlet`** when using async SQLAlchemy — it's required but not always auto-installed
- **Use lifespan** instead of deprecated `@app.on_event` for startup/shutdown
- **Match your libraries to your route type** — async routes need async-compatible libraries
- **Eager load explicitly** — never rely on lazy loading in async SQLAlchemy
- **Don't over-async** — sync routes are fine for simple, low-concurrency scenarios
- **Profile under load** — async benefits are only visible under concurrent requests; don't optimize prematurely
- **Use `attribute_names` on `refresh`** for post-commit relationship loading instead of a full re-query

### Performance Reality Check

```
Single request, no concurrency:
  sync ≈ async (async may be slightly slower due to overhead)

100 concurrent requests, DB-heavy:
  async >> sync (sync saturates thread pool; async handles more efficiently)
```

### 🎯 Interview Tip — Story to Tell
> *"On a project, I noticed our thread pool was saturating under load because we had many sync DB routes. After converting to async with asyncpg/aiosqlite and fixing our eager loading, we could handle significantly more concurrent connections with the same resources. The key learning was that async requires discipline — lazy loading doesn't work, you have to be explicit about everything you load."*

Adapt this to your own experience with the JIRA pipeline or BoA data work. Having a concrete "I saw the problem, diagnosed it, fixed it" story is worth more than any theoretical explanation.

## Quick Revision Cheat Sheet

```
async def    → runs on event loop → MUST await IO
def          → runs in thread pool → safe by default in FastAPI

await these:  db.execute() / db.commit() / db.refresh() / db.delete()
no await:     db.add()  ← in-memory only

Async DB stack:
  SQLite:     aiosqlite driver  →  sqlite+aiosqlite://
  PostgreSQL: asyncpg driver    →  postgresql+asyncpg://

Relationships in async → use selectinload() / joinedload()
  Never lazy load → MissingGreenlet error

expire_on_commit=False  ← always set this in async setup
lifespan context manager ← modern startup/shutdown (not @on_event)
greenlet ← install this or async SQLAlchemy won't work
```
